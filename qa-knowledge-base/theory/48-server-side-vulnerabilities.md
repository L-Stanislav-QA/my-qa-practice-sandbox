# 48. Server Side уязвимости: SQLi, SSRF и Broken Access Control

Серверные уязвимости — это ошибки в логике бэкенда, конфигурации серверов или способах обработки данных извне. В отличие от клиентских атак, здесь злоумышленник взаимодействует напрямую с «сердцем» системы: базой данных, файловой системой или внутренними сетевыми ресурсами. Для тестировщика поиск таких багов требует понимания того, как данные текут от API к БД и обратно. Обнаружение серверной уязвимости почти всегда означает критический (P1/P0) приоритет бага, так как это может привести к полной компрометации инфраструктуры компании.

## 1. SQL Injection (SQLi): Прямой доступ к базе

SQL-инъекция происходит, когда данные, вводимые пользователем, вставляются в SQL-запрос без должной очистки. Это позволяет атакующему «дописать» свою команду к запросу сервера.

**Пример:**
Сервер выполняет: `SELECT * FROM users WHERE id = '` + **user_id** + `'`
Если ввести в `user_id` значение `' OR '1'='1`, запрос превратится в:
`SELECT * FROM users WHERE id = '' OR '1'='1'`
Результат: сервер вернет данные **всех** пользователей, так как условие `'1'='1'` всегда верно.



**Как искать QA:**
*   Вводи одинарную кавычку `'` в поля поиска или фильтры. Если сервер выдал ошибку 500 с текстом про SQL-синтаксис — это потенциальная дыра.
*   Проверяй числовые параметры в URL: `?id=10-1`. Если сервер вернул данные для `id=9`, он вычисляет математику внутри запроса, что очень плохо.
*   **Защита:** Использование **Prepared Statements** (параметризованных запросов), где данные отделены от команд.

## 2. SSRF (Server-Side Request Forgery)

SSRF — это уязвимость, позволяющая атакующему заставить сервер отправить запрос туда, куда он не должен иметь доступа (например, во внутреннюю сеть компании или на сам сервер `localhost`).

**Пример:**
Приложение имеет функцию «Загрузить аватар по ссылке». Ты вводишь `http://169.254.169.254/latest/meta-data/` (адрес метаданных в облаке AWS). Если сервер скачивает это и показывает тебе, ты только что получил секретные ключи доступа ко всей облачной инфраструктуре.

**Как искать QA:**
*   Везде, где сервис принимает URL (загрузка файлов, вебхуки, экспорт PDF), пробуй подставлять внутренние адреса (например, `http://localhost:8080/admin`).

## 3. Broken Access Control (Ошибки контроля доступа)

Это уязвимость №1 в списке OWASP. Она случается, когда сервер не проверяет, имеет ли право текущий пользователь совершать действие над конкретным объектом.

*   **IDOR (Insecure Direct Object Reference):** Самый простой пример. Ты залогинен как пользователь №100 и видишь свой профиль по ссылке `/api/user/100`. Ты меняешь ID в ссылке на `/api/user/101` и видишь данные чужого профиля.
*   **Privilege Escalation:** Когда обычный пользователь может вызвать метод `/api/admin/delete_user`, просто зная URL, потому что сервер забыл проверить роль `isAdmin`.



**Как искать QA:**
*   Используй два разных аккаунта. Попробуй подставить ID ресурса (заказа, сообщения) от Аккаунта А в запрос от Аккаунта Б.

## 4. Insecure Deserialization и Command Injection

*   **Command Injection:** Когда данные из формы попадают напрямую в системную команду ОС. Например, сервис проверки пинга принимает IP и выполняет `os.system("ping " + ip)`. Если ввести `8.8.8.8 ; rm -rf /`, сервер может удалить все свои файлы.
*   **Insecure Deserialization:** Ошибка при превращении данных из строки (JSON, XML, бинарный формат) обратно в объект. Если сервер «доверяет» структуре объекта, атакующий может подсунуть вредоносный код, который исполнится в момент чтения данных.

## 5. Как верифицировать исправления (Re-testing)

Когда разработчик говорит «исправил SQLi», QA должен проверить:
1.  **Прямой кейс:** Тот самый payload (например, `' OR 1=1`) больше не работает.
2.  **Обход фильтров:** Проверить вариации (пробелы, кодировки URL, разные типы кавычек).
3.  **Регрессия:** Не сломался ли легитимный поиск (например, фамилия *O'Brian* с кавычкой должна сохраняться корректно).

## Вариант чек-листа по теме:

1. Понимаю ли я, как кавычка `'` помогает обнаружить потенциальную SQL-инъекцию?
2. Умею ли я проверять IDOR, меняя идентификаторы в API-запросах между двумя аккаунтами?
3. Знаю ли я разницу между вертикальным (админ vs юзер) и горизонтальным (юзер А vs юзер Б) повышением привилегий?
4. Проверяю ли я функции загрузки по ссылке на возможность SSRF атак?
5. Могу ли я объяснить разработчику, почему использование Prepared Statements лучше, чем просто фильтрация спецсимволов?
6. Понимаю ли я опасность вывода подробных ошибок бэкенда (Stack Trace) пользователю?
7. Умею ли я определять места, где ввод пользователя может попасть в системные команды сервера?
8. Проверяю ли я, что после выхода из аккаунта (Logout) старый токен или сессия действительно перестают работать на сервере?
9. Знаю ли я, как проверить безопасность API-методов `PUT`, `POST` и `DELETE` на предмет доступа без авторизации?
10. Могу ли я составить сценарий тестирования для проверки логики восстановления пароля (нельзя ли узнать чужой секрет)?
