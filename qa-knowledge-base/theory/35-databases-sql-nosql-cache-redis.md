# 35. Базы данных для QA-инженера: SQL, NoSQL, Кэширование и Redis

Любое современное приложение — это прежде всего данные. Пользователи регистрируются, делают заказы, пишут сообщения, загружают файлы — и всё это нужно где-то хранить, быстро находить и надёжно возвращать. Для QA-инженера понимание того, как устроено хранение данных, — не «бонусный» навык, а необходимость. Большинство критических багов в продакшене рождается именно на уровне данных: не та запись обновилась, кэш вернул устаревшую цену, сессия пользователя пропала после перезапуска сервера, две параллельные транзакции привели к двойному списанию денег. Чтобы находить и воспроизводить такие баги, тестировщик должен понимать, как работают реляционные и нереляционные базы данных, зачем нужен кэш и чем Redis отличается от «просто кэша».

## 1. SQL и NoSQL — фундаментальные различия

Прежде чем выбрать, как тестировать хранилище данных, нужно понять его природу. Все базы данных делятся на два больших лагеря: реляционные (SQL) и нереляционные (NoSQL). Это не вопрос «что лучше» — это вопрос «что подходит для конкретной задачи».

### Реляционные базы данных (SQL)

Реляционные СУБД — это PostgreSQL, MySQL, Oracle, Microsoft SQL Server — хранят данные в виде таблиц со строками и столбцами. Каждая таблица имеет жёсткую схему: заранее определённые поля, типы данных и ограничения. Связи между таблицами (отношения «один ко многим», «многие ко многим») обеспечиваются через внешние ключи (Foreign Keys).

Главная сила реляционных баз — **транзакции** и гарантии **ACID**:

- **Atomicity (Атомарность)** — транзакция либо выполняется целиком, либо не выполняется вообще. Если при переводе денег между счетами произошёл сбой после списания, но до зачисления — система откатит всё назад, и ни рубля не потеряется.
- **Consistency (Консистентность)** — база всегда остаётся в согласованном состоянии. Нельзя нарушить правила целостности данных (например, создать заказ, ссылающийся на несуществующего пользователя).
- **Isolation (Изолированность)** — параллельные транзакции не мешают друг другу. Два пользователя, одновременно покупающие последний товар, не купят его оба.
- **Durability (Надёжность)** — после подтверждения транзакции данные сохранены навсегда, даже при внезапном отключении питания.

SQL-базы идеально подходят для финансовых систем, ERP, CRM, интернет-магазинов — то есть везде, где важна строгая согласованность данных и сложные связи между сущностями. Язык запросов SQL позволяет делать сложные выборки с JOIN-ами, агрегациями (GROUP BY, COUNT, SUM) и фильтрацией — то, что очень пригождается тестировщику при проверке данных напрямую в БД.

Слабое место SQL — **масштабирование**. Реляционные базы масштабируются вертикально (поставить сервер мощнее), что дорого и имеет физический предел. Горизонтальное масштабирование (шардирование — разбивка данных по нескольким серверам) возможно, но очень сложно в реализации.

### Нереляционные базы данных (NoSQL)

NoSQL — это целое семейство разных подходов к хранению данных. Объединяет их одно: отказ от жёстких таблиц и реляционной модели. Основные виды:

**Документные базы (Document Store)** — MongoDB, CouchDB. Данные хранятся в виде документов в формате JSON (или BSON). Схема гибкая: у разных документов в одной «коллекции» могут быть разные поля. Идеально для каталогов товаров, где у смартфона — поле «диагональ экрана», а у куртки — «размер» и «материал».

~~~json
{
  "product_id": "SKU-12345",
  "name": "Беспроводные наушники",
  "price": 4990,
  "specs": {
    "battery_hours": 30,
    "bluetooth": "5.2",
    "noise_cancellation": true
  },
  "tags": ["audio", "wireless", "sale"]
}
~~~

**Ключ-значение (Key-Value Store)** — Redis, DynamoDB, Memcached. Простейшая модель: есть ключ, есть значение. Молниеносный поиск по ключу. Используется для сессий, кэша, счётчиков.

**Колоночные базы (Wide-Column Store)** — Apache Cassandra, HBase. Данные хранятся по столбцам, а не по строкам. Очень эффективны для аналитики, временных рядов и систем с огромным объёмом записи (IoT-телеметрия, логи).

**Графовые базы (Graph Database)** — Neo4j. Данные — это узлы и рёбра между ними. Идеально для социальных сетей, рекомендательных систем, карт маршрутов — там, где важны связи между объектами, а не сами объекты.

### Главный компромисс: CAP-теорема

Распределённые NoSQL-системы вынуждены выбирать между тремя свойствами: **Consistency** (все узлы видят одинаковые данные), **Availability** (система всегда отвечает) и **Partition Tolerance** (система продолжает работать при сетевых сбоях). Одновременно обеспечить все три невозможно — это и есть суть CAP-теоремы. Именно поэтому многие NoSQL-базы выбирают **«в конечном счёте согласованность»** (Eventual Consistency): данные со временем станут одинаковыми на всех узлах, но в момент записи разные пользователи могут видеть немного разные версии. Для социальной ленты это приемлемо. Для банковского баланса — нет.

### Что это значит для тестировщика

QA-инженер должен знать тип БД в своём проекте и понимать вытекающие из этого риски:

- В SQL-системах стоит проверять сценарии **конкурентного доступа**: что будет, если два пользователя одновременно оформят заказ на последнюю единицу товара? Корректно ли отработает блокировка или возникнет race condition?
- В NoSQL-системах с Eventual Consistency важно проверять **временные несоответствия данных**: пользователь обновил профиль, сразу зашёл на другую страницу — увидел ли он уже новые данные или ещё старые?
- При миграции данных или изменении схемы в SQL — обязательно проверять, не сломались ли Foreign Key constraints и не потерялись ли данные.
- В MongoDB и других документных базах — проверять сценарии с отсутствующими полями: код бэкенда должен корректно обрабатывать документы, у которых нет какого-то поля (а не падать с NullPointerException).

## 2. Серверное кэширование

### Зачем нужен кэш

Представьте интернет-магазин с каталогом из 50 000 товаров. Каждый раз, когда пользователь открывает главную страницу, сервер делает сложный SQL-запрос: выбирает топ-20 популярных товаров, джойнит таблицы с ценами и скидками, считает рейтинги. Этот запрос выполняется 500 миллисекунд. Если одновременно на сайт заходят 1000 пользователей — база данных получает 1000 таких запросов в секунду и начинает «задыхаться».

Решение — **кэширование**: результат тяжёлого запроса вычисляется один раз, сохраняется в быстром хранилище и при последующих запросах возвращается мгновенно, без повторного обращения к базе. Кэш — это буфер между приложением и медленным источником данных (БД, внешним API).

Операция чтения из памяти (RAM) примерно в 100–1000 раз быстрее, чем чтение с диска или сетевой запрос к БД. Именно поэтому кэш в памяти (in-memory cache) — стандартный инструмент высоконагруженных систем.

### Что кэшируется

Кэшировать имеет смысл данные, которые:
- **Часто запрашиваются** — главная страница, список категорий, топ товаров
- **Редко меняются** — справочники валют, конфигурации, список стран
- **Дорого вычисляются** — результаты сложных агрегаций, рекомендации на основе ML-модели
- **Приходят из медленных внешних источников** — курс валюты от стороннего API, данные из стороннего сервиса доставки

Кэшировать не стоит данные, которые меняются при каждом запросе (персональная корзина пользователя, баланс счёта в реальном времени) или критически важны для консистентности (финансовые транзакции).

### Стратегии хранения и инвалидации кэша

**Инвалидация кэша** (cache invalidation) — это процесс удаления или обновления устаревших данных в кэше. Это одна из самых сложных задач в разработке. Основные стратегии:

**TTL (Time To Live)** — у каждой записи в кэше есть «время жизни». Через заданный период (например, 60 секунд или 24 часа) запись автоматически удаляется, и следующий запрос снова идёт в БД за свежими данными. Просто и надёжно, но между обновлением данных в БД и истечением TTL пользователи могут видеть устаревшую информацию.

**Event-driven инвалидация** — при каждом изменении данных в БД система явно удаляет или обновляет соответствующую запись в кэше. Данные всегда актуальны, но реализация сложнее: нужно отслеживать все места, где данные меняются, и не забыть инвалидировать все связанные ключи.

**Cache-Aside (Lazy Loading)** — приложение само управляет кэшем: сначала смотрит в кэш (cache hit), если данных нет (cache miss) — идёт в БД, получает данные, кладёт их в кэш и возвращает пользователю. Гибко, но первый пользователь после инвалидации всегда получает «медленный» ответ.

**Write-Through** — запись идёт одновременно в кэш и в БД. Данные в кэше всегда актуальны, но каждая операция записи немного медленнее.

### Как кэш влияет на тестирование

Кэш — постоянный источник хитрых багов, которые воспроизводятся не с первого раза:

- После обновления данных (например, изменения цены товара администратором) пользователи ещё несколько минут видят старую цену — это не баг, если TTL настроен на 5 минут, но нужно убедиться, что команда это понимает и принимает.
- Тест проходит с первого запуска, но падает при повторном — потому что в первый раз данные шли из БД, а при повторном — из кэша, где осталось старое состояние от предыдущего теста.
- **«Холодный старт»**: после деплоя или рестарта сервиса кэш пуст, первые запросы замедлены и могут перегрузить БД — это называется «Cache Stampede» или «Thundering Herd Problem».
- Разные инстансы приложения могут иметь разный кэш, если кэш хранится локально в памяти процесса (in-process cache), а не в централизованном хранилище.

## 3. Redis — хранилище данных в памяти

### Что такое Redis и почему он особенный

**Redis** (Remote Dictionary Server) — это хранилище данных в оперативной памяти с открытым исходным кодом. В отличие от классических баз данных, которые хранят данные на диске, Redis держит всё в RAM — именно поэтому он отвечает за микросекунды. Redis поддерживает время ответа менее 1 миллисекунды даже под высокой нагрузкой, что делает его одним из самых быстрых хранилищ в мире.

Принципиальное отличие Redis от простого кэша (например, Memcached) — **богатство структур данных**. Redis — это не просто «ключ → строка». Он понимает разные типы значений и умеет с ними работать эффективно на стороне сервера.

### Структуры данных Redis

**String (Строка)** — базовый тип. Значением может быть текст, число или бинарные данные. Используется для хранения отдельных значений, счётчиков, флагов.

~~~
SET session:user:42 "eyJhbGciOiJIUzI1NiJ9..."
GET session:user:42
INCR page_views:homepage
~~~

**List (Список)** — двусвязный список строк. Поддерживает добавление в начало и конец за O(1). Используется для очередей задач, лент активности, истории последних N элементов.

~~~
LPUSH notifications:user:42 "Ваш заказ отправлен"
RPUSH task_queue "send_email:order_1234"
LRANGE notifications:user:42 0 9   # последние 10 уведомлений
~~~

**Hash (Хэш)** — словарь из пар поле-значение. Идеален для хранения объектов. Вместо того чтобы сериализовать весь JSON пользователя как строку, можно хранить его поля отдельно и обновлять только нужные.

~~~
HSET user:42 name "Иван" email "ivan@example.com" city "Москва"
HGET user:42 name
HMGET user:42 name email
~~~

**Set (Множество)** — неупорядоченный набор уникальных строк. Поддерживает операции пересечения, объединения, разности множеств. Используется для хранения тегов, уникальных посетителей, «чёрных списков».

~~~
SADD online_users "user:42" "user:77" "user:99"
SISMEMBER online_users "user:42"   # онлайн ли пользователь?
SCARD online_users                  # сколько пользователей онлайн
~~~

**Sorted Set (Упорядоченное множество, ZSet)** — множество, где каждый элемент имеет числовой «балл» (score). Элементы хранятся в отсортированном порядке по баллу. Идеально для лидербордов, топов, очередей с приоритетами.

~~~
ZADD leaderboard 15420 "user:42"
ZADD leaderboard 28900 "user:77"
ZREVRANGE leaderboard 0 9 WITHSCORES   # топ-10 игроков
ZRANK leaderboard "user:42"             # место пользователя в рейтинге
~~~

### TTL и управление жизненным циклом ключей

Каждый ключ в Redis может иметь **время жизни (TTL)**. По истечении TTL Redis автоматически удаляет ключ — это ключевой механизм для реализации сессий, временных токенов, кэша.

~~~
SET reset_token:user:42 "abc123xyz" EX 900   # токен живёт 15 минут
TTL reset_token:user:42                       # сколько секунд осталось
PERSIST reset_token:user:42                   # убрать TTL, сделать вечным
~~~

Если TTL не задан — ключ хранится вечно (или до явного удаления командой DEL). Для кэширования всегда нужно устанавливать TTL, иначе Redis может заполниться данными, которые давно устарели.

### Redis как брокер сообщений и очередь

Помимо кэша, Redis активно используется как **легковесный брокер сообщений**. Механизм **Pub/Sub** позволяет издателям публиковать сообщения в каналы, а подписчикам — получать их в реальном времени. Это используется для чатов, уведомлений, событийных систем.

~~~
# Подписчик
SUBSCRIBE notifications:new_orders

# Издатель
PUBLISH notifications:new_orders '{"order_id": 9876, "amount": 4990}'
~~~

Для надёжных очередей задач (где важно не потерять сообщение) используют структуру **List** с командами `LPUSH` / `BRPOP` — воркер блокирующе ждёт появления задачи в очереди и сразу её берёт в обработку. Более современный подход — **Redis Streams**, появившийся в Redis 5.0: это персистентный лог сообщений с группами потребителей, аналог Kafka для менее нагруженных сценариев.

### Redis как хранилище сессий

Одно из самых частых применений Redis в веб-приложениях — хранение пользовательских сессий. Когда пользователь входит в систему, сервер создаёт сессию, сохраняет её в Redis с TTL (например, 30 минут), а в cookie браузера кладёт только session ID. При каждом запросе сервер смотрит session ID из cookie, идёт в Redis и получает данные сессии за микросекунды.

Это решает несколько проблем: сессии переживают перезапуск сервера (если включена персистентность Redis), несколько инстансов приложения видят одни и те же сессии (централизованное хранилище), просроченные сессии удаляются автоматически.

### Персистентность: Redis — это не только оперативная память

Частое заблуждение: «Redis — in-memory, значит данные теряются при перезапуске». На самом деле Redis поддерживает два механизма персистентности:

**RDB (Redis Database)** — периодические снапшоты состояния в файл на диск. Компактно и быстро при старте, но между снапшотами данные могут быть потеряны при сбое.

**AOF (Append Only File)** — журнал всех операций записи. При каждой команде запись добавляется в лог. При перезапуске Redis воспроизводит весь лог и восстанавливает данные. Надёжнее, но файл растёт со временем (периодически делается rewrite).

Для продакшн-систем часто используют оба режима вместе: AOF для надёжности, RDB для быстрого восстановления после полного сбоя.

### Как тестировать сценарии с Redis

Redis порождает специфический класс багов, которые редко ловятся стандартными тестами:

**Сценарии переполнения памяти**: Redis имеет настройку `maxmemory`. При достижении лимита он применяет **политику вытеснения** (eviction policy): `allkeys-lru` (удаляет давно неиспользуемые ключи), `volatile-lru` (удаляет только ключи с TTL), `noeviction` (отказывает в записи с ошибкой). QA должен проверить поведение системы при заполненном Redis: корректно ли обрабатывается ошибка, не ломается ли критическая функциональность.

**Сценарии истечения TTL**: Что происходит, когда токен сброса пароля истекает прямо в процессе его использования? Что видит пользователь, если его сессия истекла во время заполнения формы?

**Сценарии недоступности Redis**: Что происходит с приложением, если Redis упал? Деградирует ли сервис gracefully (начинает ходить в БД, работает медленнее) или полностью падает? Настроены ли таймауты на соединение с Redis?

**Race conditions в счётчиках**: Если два воркера одновременно читают счётчик попыток входа, увеличивают его и пишут обратно — вместо INCR — возникает классическая проблема конкурентного доступа. Redis однопоточный в части выполнения команд, поэтому атомарная команда `INCR` безопасна, а паттерн «read-modify-write» из кода приложения — нет.

**Инвалидация кэша**: Обновил ли администратор цену товара, и исчезла ли старая цена из кэша? Не осталось ли в Redis ключей, которые должны были быть удалены?

## Вариант чек-листа по теме:

1. Знаю ли я, какой тип БД (SQL или NoSQL) используется в моём проекте и почему выбрали именно его?
2. Понимаю ли я, что означает «транзакция» в SQL и умею ли проверять атомарность критических операций (например, перевод средств между счетами)?
3. Проверял ли я сценарии **конкурентного доступа**: что будет, если два пользователя одновременно совершат одно и то же действие (купят последний товар, нажмут кнопку дважды)?
