# 37. Git: Машина времени и командная работа

Для многих начинающих тестировщиков Git кажется сложной и пугающей магией, нужной только разработчикам. Однако в современной инженерной культуре Git — это база. Это распределенная система контроля версий, которая позволяет отслеживать каждое изменение в коде, возвращаться к любой точке в прошлом и работать над разными фичами параллельно, не мешая друг другу. Тестировщику Git нужен, чтобы «подтягивать» свежий код автотестов, переключаться на ветку разработчика для проверки конкретной фичи до её слияния в основную ветку и, что самое важное, — проводить археологические раскопки в коде, чтобы найти корень проблемы. Знание Git делает тебя автономным: тебе не нужно просить разработчика «развернуть мне версию за прошлый четверг», ты просто делаешь это сам одной командой.

## 1. Основные понятия: Как устроена память проекта

В основе Git лежат несколько ключевых концепций, которые нужно понимать на уровне физики процесса. **Репозиторий** — это всё дерево вашего проекта вместе со всей историей его изменений. Он может быть локальным (на твоем компьютере) и удаленным (на сервере вроде GitHub или GitLab). **Коммит (Commit)** — это «снимок» состояния файлов в определенный момент времени. В отличие от простого сохранения файла, коммит в Git — это неизменяемая единица истории, у которой есть автор, дата и уникальный хэш (ID). 

Важно понимать стадии, через которые проходит файл: **Working Directory** (где ты просто правишь код), **Staging Area** (куда ты добавляешь файлы перед коммитом через `git add`) и **Repository** (где изменение сохраняется навсегда). Для тестировщика важно понимать, что если изменение не закоммичено, оно может быть потеряно или случайно затереть результаты тестов. Коммиты позволяют нам точно знать, какую именно версию приложения мы тестируем в данный момент. Если баг воспроизводится на одном коммите, но исчезает на другом — мы можем локализовать проблему до конкретных строк кода.



## 2. Ветки и слияние: Изоляция фич и релизы

Ветки (**Branches**) — это, пожалуй, самая мощная возможность Git. Представь, что основная ветка (`main` или `master`) — это стабильная версия приложения, которая работает у пользователей. Когда разработчик начинает делать новую фичу, он создает «ответвление» — копию кода, в которой он может ломать и строить всё, что угодно, не затрагивая стабильную версию. Тестировщик часто работает именно в таких ветках: тебе дают задачу на тестирование фичи «X», и ты переключаешься на ветку `feature/login-redesign`, чтобы проверить её в изоляции.

**Слияние (Merge)** — это процесс объединения изменений из одной ветки в другую. Когда тестирование фичи завершено и баги исправлены, код из ветки фичи «вливается» в основную ветку. Иногда возникают **конфликты слияния** — это ситуация, когда два человека изменили одну и ту же строку в одном файле. Тестировщик должен понимать механику слияния, чтобы осознавать риски: часто баги появляются не в самой фиче, а именно в момент её объединения с основным кодом из-за неверно разрешенных конфликтов. Понимание структуры веток помогает QA планировать регрессионное тестирование: мы смотрим, какие ветки были влиты в релиз, и понимаем, какие области системы могли пострадать.



## 3. Практическая работа: Ежедневные команды QA

Большую часть времени тестировщик использует ограниченный набор команд, но их нужно знать «на кончиках пальцев». Всё начинается с `git clone` — копирования проекта с сервера на твой компьютер. Далее идет цикл: `git pull` (забрать свежие правки коллег), `git checkout` (переключиться на нужную задачу) и запуск тестов.

~~~bash
# Склонировать репозиторий (создаст папку с проектом)
git clone https://github.com/company/project-web.git

# Посмотреть статус: в какой ты ветке и есть ли незакоммиченные изменения
git status

# Забрать последние изменения из облака и объединить со своей веткой
git pull origin main

# Перейти на ветку с новой фичей для тестирования
git checkout feature/new-payment-method

# Создать свою ветку для написания автотестов
git checkout -b qa/api-tests-for-payments

# Добавить изменения в индекс (подготовить к коммиту)
git add .

# Зафиксировать изменения с понятным сообщением
git commit -m "feat: add smoke tests for Stripe integration"

# Отправить свою ветку на сервер, чтобы коллеги её увидели
git push origin qa/api-tests-for-payments
~~~

> 💡 **Совет:** Всегда делай `git pull` перед началом тестирования. Нет ничего обиднее, чем потратить час на поиск бага, который разработчик уже исправил и запушил в репозиторий 15 минут назад.

## 4. Археология для QA: Поиск причин багов

Когда ты находишь баг, твоя ценность как инженера растет, если ты можешь сказать не только «оно сломалось», но и «это сломалось после вот этого изменения». Инструменты истории в Git — это твой микроскоп. Команда `git log` показывает список всех изменений. Ты можешь отфильтровать их по дате, автору или конкретному файлу. 

Особое место занимает команда `git blame` (в некоторых интерфейсах — Annotate). Она показывает файл построчно, и рядом с каждой строкой пишет: кто и в каком коммите её изменил последним. Если ты видишь, что логика расчета скидки изменилась вчера и именно после этого скидки перестали считаться — ты нашел «виновного». Также крайне полезен `git diff` — он подсвечивает разницу между версиями. Ты можешь сравнить текущий код с кодом недельной давности и увидеть все добавленные или удаленные строки. Это позволяет проводить «Code Review для тестировщиков», чтобы понять, какие именно части системы затронул разработчик и где стоит «потыкать» посильнее.

~~~bash
# Посмотреть краткую историю коммитов (красиво и в одну строку)
git log --oneline --graph --decorate

# Посмотреть, кто изменил каждую строку в файле (Git Blame)
git blame src/services/payment_service.py

# Сравнить текущее состояние с версией двухдневной давности
git diff HEAD@{2.days.ago} src/config.json

# Посмотреть изменения в конкретном коммите по его хэшу
git show a1b2c3d4
~~~

## 5. Удаленные репозитории и GitHub/GitLab

В реальности код живет на серверах. **GitHub, GitLab, Bitbucket** — это не сам Git, а сервисы-хостинги для него с удобным графическим интерфейсом. Для тестировщика эти платформы становятся основным местом работы с **Pull Requests (или Merge Requests)**. Это запросы разработчиков на вливание своего кода в общую ветку.

QA часто участвует в процессе PR: ты можешь оставить комментарий прямо к строке кода, прикрепить скриншот бага или запустить автоматические проверки (CI). Важно понимать концепцию **Upstream** и **Origin**. Origin — это твой «форк» или основная копия на сервере, а Upstream — первоисточник кода. Работа с удаленными репозиториями требует внимательности: всегда проверяй, в ту ли ветку ты пытаешься отправить свой код. Также на этих платформах удобно смотреть историю билдов и связывать коммиты с задачами в Jira, что создает прозрачную связь между кодом и требованиями бизнеса.

6. Умею ли я пользоваться `git log`, чтобы найти изменения, сделанные за определенный период?

8. Знаю ли я, как посмотреть разницу между двумя коммитами через `git diff`?
9. Понимаю ли я, что такое Pull Request и какова роль тестировщика в его проверке?

14. Умею ли я временно «припрятать» свои незавершенные изменения через `git stash`, если нужно срочно переключиться на другую ветку?
15. Знаю ли я, как отменить последние локальные изменения, если я случайно что-то сломал в коде тестов?
