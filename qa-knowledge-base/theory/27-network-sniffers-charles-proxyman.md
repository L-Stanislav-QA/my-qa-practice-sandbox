# 27. Снифферы: Charles Proxy и Proxyman 

**Сниффер (HTTP-прокси)** — это инструмент-посредник, который встает между мобильным устройством и сервером. Он позволяет «прослушивать», анализировать, перехватывать и изменять сетевой трафик (запросы и ответы), который генерирует мобильное приложение.

## 1. Зачем мобильному QA нужен сниффер?
1. **Локализация багов:** Определение стороны ошибки (Client vs Backend). Если в ответе сервера ошибка 500 — баг на бэкенде. Если данные верны, но не отобразились — баг на фронтенде.
2. **Мокирование (Mocking):** Подмена ответа сервера для проверки редких состояний (например, баланс в миллион или статус «Заблокирован»).
3. **Проверка безопасности:** Контроль передачи паролей и личных данных в открытом (незашифрованном) виде.
4. **Тестирование на медленном интернете:** Искусственное замедление трафика (Throttling) и обрывы связи.

## 2. Популярные инструменты
* **Charles Proxy:** Классический кроссплатформенный инструмент. Обладает огромным функционалом, но имеет сложный интерфейс.
* **Proxyman:** Современный, быстрый и интуитивно понятный инструмент. Идеально оптимизирован под macOS, имеет отличный бесплатный функционал.
* **Fiddler:** Традиционный выбор для пользователей Windows.



## 3. Технические нюансы настройки

### Связка «Телефон — Сниффер»
1. **Общая сеть:** Компьютер и телефон должны находиться в одной Wi-Fi сети.
2. **Proxy Settings:** В настройках Wi-Fi на телефоне вручную указывается IP компьютера и порт (обычно 8888).
3. **SSL Certificate:** Для чтения HTTPS-трафика необходимо установить сертификат сниффера на телефон.
    * **iOS:** Требуется вручную включить доверие сертификату в «Настройки -> Об этом устройстве -> Доверие сертификатам».
    * **Android 7+:** Приложения по умолчанию не доверяют пользовательским сертификатам. Для работы требуется файл `network_security_config.xml` в коде приложения.

### SSL Pinning — барьер безопасности
Это механизм, при котором приложение доверяет только конкретному «зашитому» сертификату сервера. 
* **Признак:** В сниффере вместо данных видны ошибки `Unknown` или `SSLHandshake`.
* **Решение:** Для тестирования QA обычно получает специальную сборку приложения с отключенным SSL Pinning.

## 4. Ключевые функции (Методы тестирования)

### А. Map Local и Map Remote
* **Map Local:** Подмена ответа сервера файлом с вашего ПК. Идеально для проверки фронтенда, когда бэкенд еще не готов.
* **Map Remote:** Перенаправление запроса с одного сервера на другой (например, с Prod на Dev-стенд).

### Б. Breakpoints (Точки останова)
Позволяет поставить запрос «на паузу» в момент передачи. Можно вручную изменить ID товара в запросе или код ошибки в ответе перед тем, как отправить их дальше.

### В. Rewrite (Автоматизация)
Автоматическая замена частей запроса/ответа по правилам (например, замена всех `status: true` на `status: false`).

### Г. Throttling (Симуляция сети)
Настройка профилей сети с задержкой (Latency), потерей пакетов и ограничением скорости.



## 5. Расширенный чек-лист: 20 сценариев тестирования API

### Валидация данных и логика
1. **Соответствие документации:** Совпадают ли ключи и типы данных в ответе с документацией (Swagger)?
2. **Пустые обязательные поля:** Что будет, если через Map Local удалить из JSON обязательное поле (например, `user_id`)?
3. **Обработка Null:** Как ведет себя интерфейс, если вместо массива `[]` сервер прислал `null`?
4. **Типы данных:** Смена числа на строку в цене — упадет ли приложение при расчете?
5. **Длинные строки:** Подмена короткого текста на 1000 символов — не «развалится» ли верстка?

### Обработка ошибок
6. **Ошибка 500 (Server Error):** Отображается ли понятная страница ошибки или бесконечный лоадер?
7. **Ошибка 401 (Unauthorized):** Происходит ли редирект на экран логина при протухании токена?
8. **Ошибка 403 (Forbidden):** Корректно ли обрабатывается отсутствие прав доступа к разделу?
9. **Ошибка 429 (Too Many Requests):** Как приложение реагирует на ограничение частоты запросов?
10. **Custom Error Messages:** Отображается ли пользователю текст ошибки, присланный сервером в JSON?

### Безопасность и заголовки
11. **Чувствительные данные:** Не передаются ли пароли или CVV в URL-параметрах запроса?
12. **Токены в Headers:** Проверка наличия и корректности заголовков `Authorization`.
13. **Кэширование:** Проверка заголовков `Cache-Control` — не кэшируются ли личные данные?
14. **User-Agent:** Передает ли приложение корректную инфо о модели устройства и версии ОС?

### Нагрузка и стресс-тесты
15. **Slow Network:** Как ведет себя приложение при ответе сервера дольше 30 секунд (Timeout)?
16. **Дублирование запросов:** Блокирует ли клиент повторные нажатия на кнопку оплаты, чтобы избежать двойного списания?
17. **Большой Response:** Подмена ответа на файл весом 50 МБ — не зависнет ли интерфейс при парсинге?

### Специфические кейсы
18. **Локализация:** Подмена языка на арабский (RTL) — готов ли интерфейс к чтению справа налево?
19. **Валюты:** Проверка отображения различных валютных символов через подмену кода валюты в ответе.
20. **Пагинация:** Что происходит, если при запросе второй страницы сервер возвращает те же данные, что и на первой?
