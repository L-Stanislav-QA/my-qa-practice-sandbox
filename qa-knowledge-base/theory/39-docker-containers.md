# 39. Docker: Изоляция и стабильность окружения

В традиционном тестировании мы часто сталкиваемся с проблемой «загрязненного» окружения: остатки старых баз данных, разные версии библиотек или специфические настройки ОС мешают проверкам. Docker решает эту проблему через контейнеризацию. В отличие от тяжелых виртуальных машин, которые эмулируют целое «железо» и требуют много ресурсов, Docker-контейнеры делят между собой ядро основной операционной системы, оставаясь при этом абсолютно изолированными друг от друга. Это позволяет запускать десятки сервисов на обычном ноутбуке. Для QA это означает возможность мгновенно создать «чистый лист» для каждого теста, провести проверку и уничтожить контейнер, не оставляя в системе никакого мусора.



## 1. Образы и Контейнеры: Чертеж и Здание

Чтобы понять Docker, нужно уяснить разницу между двумя ключевыми сущностями: **Image (Образ)** и **Container (Контейнер)**. Образ — это неизменяемый шаблон, «замороженный» снимок файловой системы, в котором есть всё необходимое: код приложения, системные утилиты и настройки. Это своего рода чертеж или рецепт. Ты можешь скачать готовый образ базы данных PostgreSQL или браузера Chrome с публичного склада **Docker Hub**. Образы версионируются с помощью тегов (например, `postgres:15` или `postgres:latest`), что позволяет тестировщику точно выбирать нужную версию софта для проверки совместимости.

Контейнер — это уже запущенный и работающий экземпляр образа. Если образ — это рецепт пирога, то контейнер — это сам пирог, который выпекается прямо сейчас. Из одного образа можно запустить хоть сто одинаковых контейнеров. Для тестировщика это открывает невероятные возможности: ты можешь запустить пять разных версий одного и того же сервиса на разных портах одновременно, чтобы сравнить их поведение или провести регрессионное тестирование. Контейнеры эфемерны: если ты что-то сломал внутри работающего контейнера, ты просто удаляешь его и запускаешь новый из того же чистого образа за пару секунд.



## 2. Dockerfile: Как создается среда тестирования

**Dockerfile** — это обычный текстовый файл с набором инструкций, по которым Docker строит твой личный образ. Это «автоматизированная инструкция по установке», которую раньше тестировщики читали в Wiki и выполняли руками. В Dockerfile прописывается всё: какая операционная система будет внутри (обычно легкий Linux вроде Alpine), какие пакеты нужно доустановить, куда положить код тестов и какую команду выполнить при старте. Знание структуры Dockerfile позволяет QA понимать, «что под капотом» у тестируемого сервиса: какие переменные окружения он ждет и какие порты открывает.

Для автотеста Dockerfile критически важен. Мы упаковываем наши тесты (например, на Pytest или Playwright) в образ, чтобы они могли запуститься в CI/CD на любом сервере без предустановленного софта. Если в Dockerfile написано `RUN pip install -r requirements.txt`, это гарантирует, что тесты всегда будут запускаться с правильным набором библиотек. Тестировщик может сам править Dockerfile, если для тестов понадобилась новая зависимость, не дожидаясь помощи DevOps-инженера. Это делает процесс тестирования автономным и предсказуемым.

~~~dockerfile
# Пример Dockerfile для запуска твоих автотестов
FROM python:3.9-slim               # Берем базовый образ с Python

WORKDIR /app                       # Создаем рабочую папку

COPY requirements.txt .             # Копируем список зависимостей
RUN pip install --no-cache-dir -r requirements.txt  # Устанавливаем их

COPY . .                           # Копируем код тестов в контейнер

# Команда, которая запустится при старте контейнера
CMD ["pytest", "tests/api", "--html=report.html"]
~~~

## 3. Docker Compose: Оркестрация для ленивых (и умных)

Современные приложения редко состоят из одного сервиса. Обычно это бэкенд, фронтенд, база данных и, возможно, брокер сообщений. Запускать каждый контейнер по отдельности через `docker run` — долго и неудобно. Для этого существует **Docker Compose**. Это инструмент, который позволяет описать всю твою инфраструктуру в одном файле `docker-compose.yml`. Одним движением (командой `docker-compose up`) ты поднимаешь сразу всю связку сервисов, которые уже «знают» друг о друге и связаны в одну сеть.

Для тестировщика Docker Compose — это спасение при интеграционном тестировании. Тебе не нужно просить разработчика «поднять стенд». Ты просто берешь конфиг из репозитория и запускаешь его локально. Compose берет на себя проброс портов (например, чтобы база данных внутри контейнера была доступна тебе на `localhost:5432`) и проброс томов (**Volumes**), чтобы логи из контейнера писались сразу в папку на твоем компьютере. Это идеальная среда для проведения исследовательского тестирования в условиях, максимально приближенных к «боевым».

~~~yaml
# Пример docker-compose.yml для QA
version: '3.8'
services:
  web-app:
    image: my-app:latest
    ports:
      - "8080:80"                  # Мапим порт контейнера 80 на наш 8080
    depends_on:
      - db                         # Запускать только после базы
  db:
    image: postgres:15
    environment:
      POSTGRES_PASSWORD: secret    # Передаем настройки через переменные
  tests:
    build: .                       # Собираем образ из текущей папки
    depends_on:
      - web-app
~~~

## 4. Команды и Трюки: Жизнь внутри контейнера

Работа в Docker требует владения терминалом. Тестировщику часто нужно «заглянуть» внутрь работающего контейнера, чтобы проверить файлы или запустить команду вручную. Для этого используется `docker exec`. Также важно уметь смотреть логи через `docker logs` — это первый шаг, если сервис внутри контейнера упал. Умение чистить систему от «зависших» контейнеров и неиспользуемых образов с помощью `docker system prune` поможет сохранить место на диске, которое Docker поглощает очень быстро.

Еще один важный аспект — **Volumes (Тома)**. По умолчанию данные в контейнере стираются после его удаления. Чтобы сохранить отчеты о тестах или скриншоты ошибок, нужно «пробросить» папку из контейнера на свой компьютер. Это позволяет тебе видеть результаты работы автотестов прямо в своей IDE, хотя сами тесты бегут в изолированном Linux-контейнере. Понимание работы сетей в Docker (Networks) поможет тебе разобраться, почему один сервис не видит другой — часто это вопрос неправильного имени хоста в конфигах.

~~~bash
# Посмотреть все запущенные контейнеры
docker ps

# Остановить и удалить все, что описано в compose-файле
docker-compose down

# Посмотреть живые логи контейнера приложения
docker logs -f web-app-container

# "Зайти" внутрь контейнера и запустить там bash-терминал
docker exec -it web-app-container /bin/bash

# Скопировать лог-файл из контейнера к себе на диск
docker cp web-app-container:/var/log/app.log ./local_app.log

# Удалить неиспользуемые образы и слои (освободить место)
docker image prune -a
~~~
