# 46. Политики безопасности браузера: SOP и CORS

Браузер — это враждебная среда, где на соседних вкладках могут быть открыты ваш онлайн-банк и вредоносный сайт. Чтобы вредоносный сайт не смог украсть данные из банковской вкладки, существуют механизмы изоляции. Для тестировщика понимание этих правил — ключ к поиску уязвимостей, связанных с утечкой данных и подделкой запросов. Ошибки в настройке этих политик на стороне сервера (особенно CORS) являются одной из самых частых находок в Bug Bounty программах, так как они буквально открывают двери для доступа к данным пользователей со сторонних ресурсов.

## 1. SOP (Same-Origin Policy): Фундамент изоляции

**Same-Origin Policy (Политика одного источника)** — это базовое правило безопасности. Оно гласит: скрипт, загруженный с одного сайта (Origin), не может получить доступ к данным (например, кукам или содержимому страницы) другого сайта. 
Origin считается одинаковым, если совпадают три параметра:
1. **Протокол** (http vs https)
2. **Хост** (example.com vs api.example.com — это разные хосты!)
3. **Порт** (80 vs 8080)



Если бы SOP не было, любой сайт, на который вы зашли, мог бы отправить JavaScript-запрос к вашей почте и прочитать ваши письма, пока вы авторизованы. Однако SOP ограничивает только чтение данных, но не всегда запрещает отправку (что ведет к CSRF-атакам, о которых поговорим позже).

## 2. CORS (Cross-Origin Resource Sharing): Легальное исключение

В современном вебе фронтенд (например, на `myapp.com`) постоянно должен запрашивать данные из API на другом домене (например, `api.myapp.com`). SOP это запрещает. Чтобы разрешить такие запросы безопасно, придумали **CORS**. Это механизм, с помощью которого сервер сообщает браузеру: «Я разрешаю сайту Х обращаться ко мне».

Работа CORS строится на HTTP-заголовках:
*   **Origin:** Браузер автоматически добавляет этот заголовок в запрос, указывая, откуда пришел скрипт.
*   **Access-Control-Allow-Origin:** Сервер отвечает этим заголовком. Если в нем указан домен отправителя или `*` (wildcard), браузер разрешит скрипту прочитать ответ.



## 3. Типовые ошибки конфигурации для QA

Тестировщик безопасности должен искать «ленивые» настройки CORS, которые делают защиту бесполезной:
1.  **Wildcard (`*`) на конфиденциальных данных:** Если API возвращает `Access-Control-Allow-Origin: *`, это значит, что любой сайт в интернете может прочитать данные ваших пользователей. Это допустимо для публичных новостей, но критическая уязвимость для личного кабинета.
2.  **Доверие поддоменам:** Если сервер разрешает запросы со всех `*.example.com`, то уязвимость на маленьком заброшенном поддомене (например, `test-site.example.com`) позволит атаковать основной сайт.
3.  **Null Origin:** Иногда разработчики разрешают `Access-Control-Allow-Origin: null`. Это позволяет локальным файлам или атакующим через специфические песочницы обходить защиту.

## 4. Preflight-запросы (Предварительная проверка)

Если запрос «сложный» (например, содержит метод `PUT`, `DELETE` или кастомные заголовки вроде `Authorization`), браузер сначала отправляет **Preflight-запрос** методом `OPTIONS`. Он спрашивает: «А можно ли мне отправить такой запрос?». 
Если сервер отвечает `200 OK` с правильными CORS-заголовками, браузер отправляет основной запрос. Для тестировщика это важная точка проверки: если вы видите в логах много ошибок `OPTIONS`, значит, CORS настроен неверно.

## 5. Практика: Как проверять CORS

Самый простой способ проверить настройки — использовать `curl` в терминале или Burp Suite:
~~~bash
# Эмулируем запрос с вредоносного сайта evil.com к нашему API
curl -H "Origin: https://evil.com" -I https://api.mysite.com/user/profile
~~~
Если в ответе ты видишь `Access-Control-Allow-Origin: https://evil.com` или `*` — у тебя проблемы. Если заголовок отсутствует или там указан только твой домен — защита работает.
