# Ручное тестирование API (Project: QA Sandbox)

В данном документе представлены тест-кейсы для ручного тестирования API эндпоинта `GET /api/users/{username}/followers`.
Объект тестирования: [QA Automation Sandbox](https://github.com/manikosto/qa-automation-sandbox)

# Примечание:
Все тесты выполняются в инструменте Postman. Запросы организованы в коллекцию "QA Sandbox API".
Для всех запросов используется базовый URL: `http://localhost:8000`

# Примечание по авторизации:
Эндпоинт защищен. Перед выполнением тестов необходимо получить `access_token` через Login и подставить его в заголовок `Authorization: Bearer <token>`.

### TC-FOLWERS-01. Успешное получение списка followers (Happy Path)
* **Описание:** Проверка успешного получения списка подписчиков существующего пользователя.
* **Обоснование:** Делаем эту проверку, потому что список followers является базовой социальной функцией профиля; пользователь должен видеть, кто подписан на выбранный аккаунт.
* **Предусловие:**
    * Сервер и база данных запущены.
    * Пользователь `alice@buzzhive.com` авторизован.
    * Получен актуальный `access_token`.
    * У пользователя `alice_dev` есть подписчики.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET Followers**
    2. Проверить, что URL запроса: `http://localhost:8000/api/users/alice_dev/followers`
    3. Во вкладке **Auth** выбрать тип "Bearer Token" и вставить актуальный `access_token`
    4. Query-параметры не указывать
    5. Нажать кнопку **Send**

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Ответ содержит JSON-объект с пагинацией:
    ```json
    {
        "items": [
            {
                "id": "uuid-строка",
                "username": "bob_photo",
                "display_name": "Bob Photographer",
                "avatar_url": "строка или null",
                "is_verified": false
            }
        ],
        "total": 1,
        "page": 1,
        "per_page": 20,
        "pages": 1
    }
    ```
    * Поле `items` является массивом.
    * Каждый объект в `items` соответствует схеме `UserBrief`.

### TC-FOLWERS-02. Получение followers с пагинацией
* **Описание:** Проверка работы query-параметров `page` и `per_page`.
* **Обоснование:** Делаем эту проверку, потому что у популярных пользователей может быть много подписчиков; без пагинации API будет отдавать слишком большой объем данных и ухудшать производительность.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * У пользователя `alice_dev` есть больше 2 подписчиков, или тестовая база подготовлена под этот сценарий.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET Followers**
    2. Во вкладке **Auth** указать актуальный Bearer Token
    3. Выполнить запрос:
       ```text
       GET http://localhost:8000/api/users/alice_dev/followers?page=1&per_page=2
       ```
    4. Проверить поля пагинации в ответе

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * `page` равен `1`.
    * `per_page` равен `2`.
    * В массиве `items` не больше 2 пользователей.
    * `total` содержит общее количество подписчиков пользователя.
    * `pages` содержит рассчитанное количество страниц.

* **Ожидаемый результат:**

### TC-FOLWERS-04. Пользователи в списке реально являются followers
* **Описание:** Проверка, что каждый пользователь в ответе действительно подписан на пользователя из path-параметра.
* **Обоснование:** Делаем эту проверку, потому что список followers должен отражать реальные связи подписки; неверные пользователи в списке ломают социальную модель и счетчики профиля.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * У `alice_dev` есть подписчики.
    * Доступна проверка через БД или через связанный endpoint.
* **Шаги:**
    1. Выполнить GET `/api/users/alice_dev/followers`
    2. Сохранить список `username` из `items`
    3. Сверить этих пользователей с данными подписок в БД или с ожидаемыми тестовыми данными
    4. Выполнить GET `/api/users/alice_dev` и сравнить `followers_count` с `total`

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Каждый пользователь из `items` действительно подписан на `alice_dev`.
    * Поле `total` совпадает с количеством подписчиков по данным профиля/БД.

### TC-FOLWERS-05. Текущий пользователь видит себя в followers, если подписан

* **Обоснование:** Делаем эту проверку, потому что список followers должен быть объективным и не должен скрывать текущего пользователя, если его подписка существует; иначе счетчики и списки будут расходиться.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.

    2. Выполнить GET `/api/users/bob_photo/followers` с токеном `alice_dev`
    3. Проверить список `items`

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * В `items` присутствует пользователь `alice_dev`.

    1. Выполнить GET `/api/users/dave_quiet`

* **Ожидаемый результат:**
    * Статус: `200 OK` с допустимым списком followers или `403 Forbidden`, в зависимости от продуктовой логики приватности.
    * **Критично:** поведение должно быть согласовано с правилами приватности продукта.

    1. Выполнить GET `/api/users/alice_dev/followers`
    2. Проверить каждый объект в `items`
    3. Убедиться, что среди followers нет `frank_banned`

* **Ожидаемый результат:**

### TC-FOLWERS-08. Проверка структуры `PaginatedResponse_UserBrief`
* **Описание:** Проверка соответствия ответа OpenAPI-схеме `PaginatedResponse_UserBrief`.
* **Обоснование:** Делаем эту проверку, потому что frontend зависит от стабильной структуры пагинации и краткого профиля пользователя; неверный контракт может сломать экран followers.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * У `alice_dev` есть хотя бы один подписчик.
* **Шаги:**
    1. Выполнить GET `/api/users/alice_dev/followers`
    2. Проверить верхнеуровневые поля ответа
    3. Проверить структуру каждого объекта в `items`

* **Ожидаемый результат:**

        - `items` (array)
        - `total` (integer)
        - `page` (integer)

### TC-FOLWERS-09. Запрос без токена (Unauthorized)

### TC-FOLWERS-11. Запрос с просроченным токеном

* **Обоснование:** Делаем эту проверку, потому что access token имеет ограниченный срок жизни; если API принимает просроченные токены, старая сессия сможет читать социальные связи.
* **Предусловие:**

* **Шаги:**

    2. Во вкладке **Auth** вставить просроченный Bearer Token
    3. Выполнить GET `/api/users/alice_dev/followers`

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized`
    * Ответ содержит сообщение об истекшем или невалидном токене:
    ```json
    {
        "detail": "Token has expired"
    }
    ```
    * Список followers не возвращается.

### TC-FOLWERS-13. `username` с некорректными символами
* **Описание:** Проверка обработки значения `username`, которое содержит символы, не используемые в валидных username.
* **Обоснование:** Делаем эту проверку, потому что path-параметр может быть введен вручную; API должен безопасно обработать некорректное значение и не падать.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
* **Шаги:**
    1. Выполнить запрос с URL-encoded значением:
       ```text
       GET http://localhost:8000/api/users/%40%23%24%25/followers
       ```
    2. Проверить статус и тело ответа

* **Ожидаемый результат:**
    * Статус: `404 Not Found` или `422 Unprocessable Entity`, в зависимости от реализации валидации path-параметра.
    * **Критично:** отсутствует ошибка `500 Internal Server Error`.
