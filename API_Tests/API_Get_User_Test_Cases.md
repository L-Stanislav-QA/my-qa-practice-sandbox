# Ручное тестирование API (Project: QA Sandbox)

В данном документе представлены тест-кейсы для ручного тестирования API эндпоинта `GET /api/users/{username}`.
Объект тестирования: [QA Automation Sandbox](https://github.com/manikosto/qa-automation-sandbox)

# Примечание:
Все тесты выполняются в инструменте Postman. Запросы организованы в коллекцию "QA Sandbox API".
Для всех запросов используется базовый URL: `http://localhost:8000`

# Примечание по авторизации:
Эндпоинт защищен. Перед выполнением тестов необходимо получить `access_token` через Login и подставить его в заголовок `Authorization: Bearer <token>`.

## План тестирования эндпоинта GET /api/users/{username}

### 2. Блок: Бизнес-логика и данные профиля (P1)
* **[USR-GET-04](#tc-usr-get-04-проверка-флагов-following-followed_by) Проверка флагов `is_following` и `is_followed_by`.** Проверка корректности relationship-полей относительно текущего пользователя.
* **[USR-GET-05](#tc-usr-get-05-проверка-счетчиков-профиля) Проверка счетчиков профиля.** Проверка полей `followers_count`, `following_count`, `posts_count`.
* **[USR-GET-06](#tc-usr-get-06-проверка-структуры-userresponse) Проверка структуры `UserResponse`.** Проверка соответствия ответа API-спецификации.

### 3. Блок: Безопасность и авторизация (P1)
* **[USR-GET-07](#tc-usr-get-07-запрос-без-токена-unauthorized) Запрос без токена (Unauthorized).** Проверка запрета доступа без авторизации.
* **[USR-GET-08](#tc-usr-get-08-запрос-с-некорректным-токеном) Запрос с некорректным токеном.** Проверка обработки невалидного Bearer token.
* **[USR-GET-09](#tc-usr-get-09-запрос-с-просроченным-токеном) Запрос с просроченным токеном.** Проверка запрета доступа по expired access_token.

### 4. Блок: Негативные проверки username (P2)
* **[USR-GET-10](#tc-usr-get-10-несуществующий-username) Несуществующий `username`.** Проверка корректной ошибки для отсутствующего пользователя.
* **[USR-GET-11](#tc-usr-get-11-username-с-некорректными-символами) `username` с некорректными символами.** Проверка устойчивости к значениям, не похожим на username.
* **[USR-GET-12](#tc-usr-get-12-sql-инъекция-в-username) SQL-инъекция в `username`.** Проверка устойчивости endpoint'а к injection payload в path-параметре.
* **[USR-GET-13](#tc-usr-get-13-чувствительность-username-к-регистру) Чувствительность `username` к регистру.** Проверка поведения при изменении регистра символов.
* **[USR-GET-14](#tc-usr-get-14-проверка-метода-post-вместо-get) Проверка метода POST вместо GET.** Проверка, что endpoint не принимает неподдерживаемый HTTP-метод.

### TC-USR-GET-01. Успешное получение публичного профиля (Happy Path)
* **Описание:** Проверка получения данных существующего публичного пользователя по `username`.
* **Обоснование:** Делаем эту проверку, потому что это основной сценарий ручки: авторизованный пользователь должен открыть профиль другого пользователя по username, чтобы посмотреть информацию, счетчики и социальный статус.
* **Предусловие:**
    * Сервер и база данных запущены.
    * Пользователь `alice@buzzhive.com` авторизован.
    * Получен актуальный `access_token`.
    * В базе есть пользователь `bob_photo`.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET User**
    2. Проверить, что URL запроса: `http://localhost:8000/api/users/bob_photo`
    3. Во вкладке **Auth** выбрать тип "Bearer Token" и вставить актуальный `access_token`
    4. Нажать кнопку **Send**

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Ответ содержит профиль пользователя `bob_photo`:
    ```json
    {
        "id": "uuid-строка",
        "email": "bob@buzzhive.com",
        "username": "bob_photo",
        "display_name": "Bob Photographer",
        "bio": "строка или null",
        "avatar_url": "строка или null",
        "cover_url": "строка или null",
        "role": "user",
        "is_active": true,
        "is_verified": false,
        "is_private": false,
        "created_at": "ISO 8601 дата-время",
        "updated_at": "ISO 8601 дата-время",
        "followers_count": 0,
        "following_count": 0,
        "posts_count": 0,
        "is_following": false,
        "is_followed_by": false
    }
    ```
    * Поле `username` равно `"bob_photo"`.

### TC-USR-GET-02. Получение собственного профиля через `username`
* **Описание:** Проверка получения профиля текущего пользователя через endpoint `GET /api/users/{username}`.
* **Обоснование:** Делаем эту проверку, потому что пользователь может открыть свой профиль не только через `/api/auth/me`, но и через публичный маршрут профиля; данные должны быть консистентны и не ломать экран профиля.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * Получен актуальный `access_token`.
* **Шаги:**
    1. Выполнить GET `/api/auth/me` и сохранить `username` текущего пользователя
    2. Выполнить GET `/api/users/alice_dev`
    3. Сравнить ключевые поля двух ответов

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Поле `username` равно `"alice_dev"`.
    * Поля `id`, `email`, `display_name`, `role`, `is_active`, `is_private` совпадают с ответом GET `/api/auth/me`.
    * Значения relationship-флагов для собственного профиля не противоречат бизнес-логике приложения.

### TC-USR-GET-04. Проверка флагов `is_following` и `is_followed_by`
* **Описание:** Проверка relationship-флагов в профиле пользователя относительно текущего авторизованного пользователя.
* **Обоснование:** Делаем эту проверку, потому что UI кнопок Follow/Unfollow и статусы подписки зависят от `is_following` и `is_followed_by`; неверные значения могут привести к неправильным действиям в интерфейсе.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * Известно, подписан ли `alice_dev` на `bob_photo` и подписан ли `bob_photo` на `alice_dev`.
    * Данные можно проверить через GET `/api/users/alice_dev/following`, GET `/api/users/alice_dev/followers` или в БД.
* **Шаги:**
    1. Проверить фактическое состояние подписок между `alice_dev` и `bob_photo`
    2. Выполнить GET `/api/users/bob_photo` с токеном `alice_dev`
    3. Проверить поля `is_following` и `is_followed_by`

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * `is_following` показывает, подписан ли текущий пользователь `alice_dev` на `bob_photo`.
    * `is_followed_by` показывает, подписан ли `bob_photo` на текущего пользователя `alice_dev`.
    * Значения флагов совпадают с фактическими данными подписок.

### TC-USR-GET-05. Проверка счетчиков профиля
* **Описание:** Проверка корректности счетчиков `followers_count`, `following_count`, `posts_count`.
* **Обоснование:** Делаем эту проверку, потому что счетчики отображаются в профиле и влияют на доверие к данным; расхождение с фактическими подписками или постами будет заметно пользователю и может указывать на ошибки агрегации.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * В базе есть пользователь `alice_dev`.
* **Шаги:**
    1. Выполнить GET `/api/users/alice_dev`
    2. Сохранить значения `followers_count`, `following_count`, `posts_count`
    3. Сравнить `followers_count` с количеством элементов/total из GET `/api/users/alice_dev/followers`
    4. Сравнить `following_count` с количеством элементов/total из GET `/api/users/alice_dev/following`
    5. Сравнить `posts_count` с количеством элементов/total из GET `/api/users/alice_dev/posts`

* **Ожидаемый результат:**
    * Статус GET `/api/users/alice_dev`: `200 OK`
    * Все счетчики являются integer и не меньше `0`.
    * Счетчики соответствуют фактическим данным связанных endpoint'ов или данным БД.

### TC-USR-GET-07. Запрос без токена (Unauthorized)
* **Описание:** Проверка запрета доступа к профилю пользователя без авторизации.
* **Обоснование:** Делаем эту проверку, потому что endpoint защищен `HTTPBearer`; если профиль доступен без токена, API может раскрывать пользовательские данные анонимным клиентам.
* **Предусловие:** Нет.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET User**
    2. Проверить URL: `http://localhost:8000/api/users/bob_photo`
    3. Во вкладке **Auth** выбрать "No Auth"
    4. Убедиться, что заголовок `Authorization` отсутствует
    5. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized` или `403 Forbidden`
    * Ответ содержит сообщение об ошибке авторизации:
    ```json
    {
        "detail": "Not authenticated"
    }
    ```
    * Данные профиля не возвращаются как успешный ответ.

### TC-USR-GET-08. Запрос с некорректным токеном
* **Описание:** Проверка обработки невалидного Bearer token.
* **Обоснование:** Делаем эту проверку, потому что сервер должен валидировать подпись и формат токена; принятие случайной строки вместо токена создает риск несанкционированного доступа.
* **Предусловие:** Нет.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET User**
    2. Во вкладке **Auth** выбрать тип "Bearer Token"
    3. Вставить невалидный токен:
       ```text
       invalid_token_12345
       ```
    4. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized` или `403 Forbidden`
    * Ответ содержит сообщение о невозможности проверить учетные данные:
    ```json
    {
        "detail": "Could not validate credentials"
    }
    ```
    * Данные профиля не возвращаются.

### TC-USR-GET-09. Запрос с просроченным токеном

* **Предусловие:**

* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET User**
    2. Во вкладке **Auth** вставить просроченный Bearer Token
    3. Проверить URL: `http://localhost:8000/api/users/bob_photo`
    4. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized`
    * Ответ содержит сообщение об истекшем или невалидном токене:
    ```json
    {
        "detail": "Token has expired"
    }
    ```
    * Данные профиля не возвращаются.

### TC-USR-GET-11. `username` с некорректными символами
* **Описание:** Проверка обработки значения `username`, которое содержит символы, не используемые в валидных username.
* **Обоснование:** Делаем эту проверку, потому что path-параметр приходит от клиента и может быть введен вручную; API должен устойчиво обработать некорректные символы и не падать с серверной ошибкой.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET User**
    2. Во вкладке **Auth** указать актуальный Bearer Token
    3. Выполнить запрос с URL-encoded значением:
       ```text
       GET http://localhost:8000/api/users/%40%23%24%25
       ```
    4. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `404 Not Found` или `422 Unprocessable Entity`, в зависимости от реализации валидации path-параметра.
    * **Критично:** отсутствует ошибка `500 Internal Server Error`.
    * Данные какого-либо существующего пользователя не возвращаются.

---

### TC-USR-GET-12. SQL-инъекция в `username`
* **Описание:** Проверка устойчивости endpoint'а к injection payload в path-параметре `username`.
* **Обоснование:** Делаем эту проверку, потому что `username` используется для поиска пользователя; если значение небезопасно попадает в запрос к БД, возможны SQL-инъекции, обход логики поиска или серверные ошибки.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * Сервер и база данных доступны.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET User**
    2. Во вкладке **Auth** указать актуальный Bearer Token
    3. Выполнить запрос с URL-encoded payload:
       ```text
       GET http://localhost:8000/api/users/%27%20OR%201%3D1%20--
       ```
    4. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `404 Not Found` или `422 Unprocessable Entity`.
    * **Критично:** отсутствует ошибка `500 Internal Server Error`.
    * API не возвращает профиль первого пользователя из базы и не возвращает список пользователей.
    * SQL payload обрабатывается как обычное значение path-параметра, а не как часть SQL-запроса.

### TC-USR-GET-13. Чувствительность `username` к регистру
* **Описание:** Проверка поведения API при передаче существующего username в другом регистре.
* **Обоснование:** Делаем эту проверку, потому что система должна иметь предсказуемое правило для username: либо строгое совпадение, либо case-insensitive поиск; неопределенное поведение может привести к дублям профилей и ошибкам навигации.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * В базе есть пользователь `bob_photo`.
* **Шаги:**
    1. Выполнить GET `/api/users/bob_photo` и убедиться, что профиль существует
    2. Выполнить GET `/api/users/BOB_PHOTO`
    3. Сравнить результат с ожидаемым правилом продукта

* **Ожидаемый результат:**
    * Если username должен быть case-sensitive: статус `404 Not Found`.
    * Если username должен быть case-insensitive: статус `200 OK`, поле `username` в ответе равно каноническому значению `"bob_photo"`.
    * **Критично:** поведение должно быть стабильным и одинаковым при повторных запросах.

### TC-USR-GET-14. Проверка метода POST вместо GET
* **Описание:** Проверка, что endpoint не принимает неподдерживаемый HTTP-метод `POST`.
* **Обоснование:** Делаем эту проверку, потому что ручка предназначена только для чтения профиля через GET; принятие POST может означать некорректную настройку роутинга и привести к непредсказуемому поведению API.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
* **Шаги:**
    1. В Postman создать или выбрать запрос к URL `http://localhost:8000/api/users/bob_photo`
    2. Установить метод `POST`
    3. Во вкладке **Auth** указать актуальный Bearer Token
    4. Тело запроса не отправлять
    5. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `405 Method Not Allowed` или `404 Not Found`, в зависимости от реализации роутинга.
    * Успешный статус `200 OK` не возвращается.
    * Профиль пользователя не возвращается как результат POST-запроса.
