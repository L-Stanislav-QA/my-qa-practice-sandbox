# Ручное тестирование API (Project: QA Sandbox)

В данном документе представлены тест-кейсы для ручного тестирования API эндпоинта `GET /api/users/{username}/posts`.
Объект тестирования: [QA Automation Sandbox](https://github.com/manikosto/qa-automation-sandbox)

# Примечание:
Все тесты выполняются в инструменте Postman. Запросы организованы в коллекцию "QA Sandbox API".
Для всех запросов используется базовый URL: `http://localhost:8000`

# Примечание по авторизации:
Эндпоинт защищен. Перед выполнением тестов необходимо получить `access_token` через Login и подставить его в заголовок `Authorization: Bearer <token>`.

### TC-USR-POSTS-01. Успешное получение постов пользователя (Happy Path)
* **Описание:** Проверка успешного получения списка постов существующего пользователя.
* **Обоснование:** Делаем эту проверку, потому что это основной сценарий ручки: профиль пользователя должен отображать его посты, а UI зависит от корректного списка и пагинации.
* **Предусловие:**
    * Сервер и база данных запущены.
    * Пользователь `alice@buzzhive.com` авторизован.
    * Получен актуальный `access_token`.
    * У пользователя `alice_dev` есть посты.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET User Posts**
    2. Проверить, что URL запроса: `http://localhost:8000/api/users/alice_dev/posts`
    3. Во вкладке **Auth** выбрать тип "Bearer Token" и вставить актуальный `access_token`
    4. Query-параметры не указывать
    5. Нажать кнопку **Send**

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Ответ содержит JSON-объект с пагинацией:
    ```json
    {
        "items": [
            {
                "id": "uuid-строка",
                "author": {
                    "id": "uuid-строка",
                    "username": "alice_dev",
                    "display_name": "Alice Developer",
                    "avatar_url": "строка или null",
                    "is_verified": true
                },
                "content": "текст поста",
                "image_url": "строка или null",
                "is_pinned": false,
                "is_deleted": false,
                "parent_id": null,
                "repost_type": null,
                "visibility": "public",
                "likes_count": 0,
                "comments_count": 0,
                "reposts_count": 0,
                "hashtags": [],
                "created_at": "ISO 8601 дата-время",
                "updated_at": "ISO 8601 дата-время",
                "is_liked": false,
                "is_bookmarked": false,
                "user_reaction": null
            }
        ],
        "total": 8,
        "page": 1,
        "per_page": 20,
        "pages": 1
    }
    ```
    * Поле `items` является массивом.
    * Поля `page` и `per_page` соответствуют значениям по умолчанию: `1` и `20`.

### TC-USR-POSTS-02. Получение постов с пагинацией
* **Описание:** Проверка работы query-параметров `page` и `per_page`.
* **Обоснование:** Делаем эту проверку, потому что у пользователя может быть много постов; без корректной пагинации профиль будет загружаться медленно и может отдавать слишком большой объем данных.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * У пользователя `alice_dev` есть больше 2 постов.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET User Posts**
    2. Во вкладке **Auth** указать актуальный Bearer Token
    3. Выполнить запрос:
       ```text
       GET http://localhost:8000/api/users/alice_dev/posts?page=1&per_page=2
       ```
    4. Проверить поля пагинации в ответе

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * `page` равен `1`.
    * `per_page` равен `2`.
    * В массиве `items` не больше 2 постов.
    * `total` содержит общее количество постов пользователя.
    * `pages` содержит рассчитанное количество страниц.

### TC-USR-POSTS-03. Получение пустого списка постов
* **Описание:** Проверка ответа для пользователя без постов.
* **Обоснование:** Делаем эту проверку, потому что пустой профиль является нормальным состоянием, особенно для нового пользователя; API должен вернуть пустой список, а не ошибку.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * Пользователь `eve_new` существует и не имеет постов.
* **Шаги:**
    1. Выполнить GET `/api/users/eve_new/posts`
    2. Проверить статус ответа
    3. Проверить поля пагинации и массив `items`

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * `items` равен пустому массиву `[]`.
    * `total` равен `0`.
    * `pages` равен `0` или `1`, в зависимости от принятой продуктовой логики пагинации.
    * Ошибка `404` или `500` не возвращается.

### TC-USR-POSTS-04. Посты принадлежат запрошенному пользователю
* **Описание:** Проверка, что каждый пост в ответе принадлежит пользователю из path-параметра `username`.
* **Обоснование:** Делаем эту проверку, потому что смешивание постов разных авторов в профиле нарушит бизнес-логику и введет пользователя в заблуждение.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * У `bob_photo` есть посты.
* **Шаги:**
    1. Выполнить GET `/api/users/bob_photo/posts`
    2. Проверить каждый объект в `items`
    3. Сравнить `author.username` каждого поста со значением `bob_photo`

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * У каждого поста в `items` поле `author.username` равно `"bob_photo"`.
    * В ответе нет постов других пользователей.

### TC-USR-POSTS-05. Получение постов приватного пользователя без подписки
* **Описание:** Проверка доступа к постам приватного пользователя, если текущий пользователь не подписан на него.
* **Обоснование:** Делаем эту проверку, потому что приватность профиля должна ограничивать доступ к контенту; если посты приватного пользователя видны без подписки, это нарушение приватности.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
    * Пользователь `dave_quiet` имеет `is_private=true`.
    * `eve_new` не имеет подтвержденной подписки на `dave_quiet`.
* **Шаги:**
    1. Выполнить GET `/api/users/dave_quiet`
    2. Убедиться, что `is_private=true` и `is_following=false`
    3. Выполнить GET `/api/users/dave_quiet/posts`

* **Ожидаемый результат:**
    * Статус: `200 OK` с пустым `items` или `403 Forbidden`, в зависимости от продуктовой логики приватности.
    * Если возвращается `200 OK`, приватные посты не раскрываются пользователю без подписки.
    * **Критично:** приватный контент не должен быть доступен неавторизованному follower-сценарию.

### TC-USR-POSTS-06. Получение постов приватного пользователя с подпиской
* **Описание:** Проверка доступа к постам приватного пользователя после подтвержденной подписки.
* **Обоснование:** Делаем эту проверку, потому что приватность должна ограничивать доступ только для неподписанных пользователей; подтвержденный follower должен видеть разрешенный контент.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * У `alice_dev` есть подтвержденная подписка на `dave_quiet`, или тестовая среда подготовлена для такого состояния.
    * У `dave_quiet` есть посты.
* **Шаги:**
    1. Проверить через GET `/api/users/dave_quiet`, что для текущего пользователя `is_following=true`
    2. Выполнить GET `/api/users/dave_quiet/posts`
    3. Проверить список постов

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Если у `dave_quiet` есть посты, они возвращаются в `items`.
    * Каждый пост принадлежит `dave_quiet`.

### TC-USR-POSTS-07. Проверка, что удаленные посты не показываются обычному пользователю
* **Описание:** Проверка фильтрации удаленных постов в списке постов пользователя.
* **Обоснование:** Делаем эту проверку, потому что удаленный контент не должен отображаться в обычном профиле; иначе пользователь увидит данные, которые автор или модератор уже удалил.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * В базе есть удаленный пост пользователя `bob_photo` с `is_deleted=true`, или тестовая среда позволяет подготовить такой пост.
* **Шаги:**
    1. Выполнить GET `/api/users/bob_photo/posts`
    2. Проверить поле `is_deleted` у каждого объекта в `items`
    3. При необходимости сверить с БД список удаленных постов пользователя

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * В `items` отсутствуют посты с `is_deleted=true`, если обычный пользователь не должен видеть удаленный контент.
    * У пользователя не раскрывается содержимое удаленных постов.

### TC-USR-POSTS-08. Проверка структуры `PaginatedResponse_PostResponse`
* **Описание:** Проверка соответствия ответа OpenAPI-схеме `PaginatedResponse_PostResponse`.
* **Обоснование:** Делаем эту проверку, потому что frontend профиля зависит от стабильной структуры пагинации и поста; отсутствие поля или неверный тип может сломать отображение ленты пользователя.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * У `alice_dev` есть хотя бы один пост.
* **Шаги:**
    1. Выполнить GET `/api/users/alice_dev/posts`
    2. Проверить верхнеуровневые поля ответа
    3. Проверить структуру каждого объекта в `items`

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Ответ содержит поля:
        - `items` (array)
        - `total` (integer)
        - `page` (integer)
        - `per_page` (integer)
        - `pages` (integer)
    * Каждый объект в `items` содержит поля `PostResponse`:
        - `id` (string, UUID)
        - `author` (UserBrief)
        - `content` (string)
        - `image_url` (string или null)
        - `is_pinned` (boolean)
        - `is_deleted` (boolean)
        - `parent_id` (string UUID или null)
        - `repost_type` (string или null)
        - `visibility` (string)
        - `likes_count` (integer)
        - `comments_count` (integer)
        - `reposts_count` (integer)
        - `hashtags` (array)
        - `created_at` (string, ISO 8601 date-time)
        - `updated_at` (string, ISO 8601 date-time)
        - `is_liked` (boolean)
        - `is_bookmarked` (boolean)
        - `user_reaction` (string или null)

### TC-USR-POSTS-09. Запрос без токена (Unauthorized)
* **Описание:** Проверка запрета доступа к списку постов пользователя без авторизации.
* **Обоснование:** Делаем эту проверку, потому что endpoint защищен `HTTPBearer`; без токена сервер не должен раскрывать ленту профиля и relationship-зависимые поля постов.
* **Предусловие:** Нет.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET User Posts**
    2. Проверить URL: `http://localhost:8000/api/users/alice_dev/posts`
    3. Во вкладке **Auth** выбрать "No Auth"
    4. Убедиться, что заголовок `Authorization` отсутствует
    5. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized` или `403 Forbidden`
    * Ответ содержит сообщение об ошибке авторизации:
    ```json
    {
        "detail": "Not authenticated"
    }
    ```
    * Список постов не возвращается как успешный ответ.

### TC-USR-POSTS-10. Запрос с некорректным токеном
* **Описание:** Проверка обработки невалидного Bearer token.
* **Обоснование:** Делаем эту проверку, потому что сервер должен валидировать токен перед выдачей данных профиля; принятие случайной строки вместо токена создает риск несанкционированного доступа.
* **Предусловие:** Нет.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET User Posts**
    2. Во вкладке **Auth** выбрать тип "Bearer Token"
    3. Вставить невалидный токен:
       ```text
       invalid_token_12345
       ```
    4. Выполнить GET `/api/users/alice_dev/posts`

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized` или `403 Forbidden`
    * Ответ содержит сообщение о невозможности проверить учетные данные:
    ```json
    {
        "detail": "Could not validate credentials"
    }
    ```
    * Список постов не возвращается.

### TC-USR-POSTS-11. Запрос с просроченным токеном
* **Описание:** Проверка запрета доступа с истекшим `access_token`.
* **Обоснование:** Делаем эту проверку, потому что access token имеет ограниченный срок жизни; если API принимает просроченные токены, старая сессия сможет читать данные профилей.
* **Предусловие:**
    * Есть `access_token`, срок действия которого истек, или тестовая среда позволяет подготовить expired token.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET User Posts**
    2. Во вкладке **Auth** вставить просроченный Bearer Token
    3. Выполнить GET `/api/users/alice_dev/posts`

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized`
    * Ответ содержит сообщение об истекшем или невалидном токене:
    ```json
    {
        "detail": "Token has expired"
    }
    ```
    * Список постов не возвращается.

### TC-USR-POSTS-12. Несуществующий `username`
* **Описание:** Проверка ответа при запросе постов пользователя, которого нет в базе.
* **Обоснование:** Делаем эту проверку, потому что клиент может открыть старую или некорректную ссылку профиля; API должен вернуть понятную ошибку, а не пустую ленту несуществующего пользователя.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * В базе отсутствует пользователь `unknown_user_999`.
* **Шаги:**
    1. Выполнить запрос:
       ```text
       GET http://localhost:8000/api/users/unknown_user_999/posts
       ```
    2. Проверить статус и тело ответа

* **Ожидаемый результат:**
    * Статус: `404 Not Found`
    * Ответ содержит сообщение о том, что пользователь не найден:
    ```json
    {
        "detail": "User not found"
    }
    ```
