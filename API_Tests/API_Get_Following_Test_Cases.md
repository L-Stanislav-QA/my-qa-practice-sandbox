# Ручное тестирование API (Project: QA Sandbox)

В данном документе представлены тест-кейсы для ручного тестирования API эндпоинта `GET /api/users/{username}/following`.
Объект тестирования: [QA Automation Sandbox](https://github.com/manikosto/qa-automation-sandbox)

# Примечание:
Все тесты выполняются в инструменте Postman. Запросы организованы в коллекцию "QA Sandbox API".
Для всех запросов используется базовый URL: `http://localhost:8000`

# Примечание по авторизации:
Эндпоинт защищен. Перед выполнением тестов необходимо получить `access_token` через Login и подставить его в заголовок `Authorization: Bearer <token>`.

### TC-FLWING-01. Успешное получение списка following (Happy Path)
* **Описание:** Проверка успешного получения списка пользователей, на которых подписан существующий пользователь.
* **Обоснование:** Делаем эту проверку, потому что список following является базовой социальной функцией профиля; пользователь должен видеть, за кем следит выбранный аккаунт.
* **Предусловие:**
    * Сервер и база данных запущены.
    * Пользователь `alice@buzzhive.com` авторизован.
    * Получен актуальный `access_token`.
    * У пользователя `alice_dev` есть исходящие подписки.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET Following**
    2. Проверить, что URL запроса: `http://localhost:8000/api/users/alice_dev/following`
    3. Во вкладке **Auth** выбрать тип "Bearer Token" и вставить актуальный `access_token`
    4. Query-параметры не указывать
    5. Нажать кнопку **Send**

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Ответ содержит JSON-объект с пагинацией:
    ```json
    {
        "items": [
            {
                "id": "uuid-строка",
                "username": "bob_photo",
                "display_name": "Bob Photographer",
                "avatar_url": "строка или null",
                "is_verified": false
            }
        ],
        "total": 1,
        "page": 1,
        "per_page": 20,
        "pages": 1
    }
    ```
    * Поле `items` является массивом.
    * Каждый объект в `items` соответствует схеме `UserBrief`.

### TC-FLWING-02. Получение following с пагинацией
* **Описание:** Проверка работы query-параметров `page` и `per_page`.
* **Обоснование:** Делаем эту проверку, потому что пользователь может быть подписан на много аккаунтов; без пагинации API будет отдавать слишком большой объем данных и ухудшать производительность.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * У пользователя `alice_dev` есть больше 2 подписок, или тестовая база подготовлена под этот сценарий.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET Following**
    2. Во вкладке **Auth** указать актуальный Bearer Token
    3. Выполнить запрос:
       ```text
       GET http://localhost:8000/api/users/alice_dev/following?page=1&per_page=2
       ```
    4. Проверить поля пагинации в ответе

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * `page` равен `1`.
    * `per_page` равен `2`.
    * В массиве `items` не больше 2 пользователей.
    * `total` содержит общее количество подписок пользователя.
    * `pages` содержит рассчитанное количество страниц.

### TC-FLWING-03. Получение пустого списка following
* **Описание:** Проверка ответа для пользователя без исходящих подписок.
* **Обоснование:** Делаем эту проверку, потому что отсутствие following является нормальным состоянием для нового пользователя; API должен вернуть пустой список, а не ошибку.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * Пользователь `eve_new` существует и ни на кого не подписан.
* **Шаги:**
    1. Выполнить GET `/api/users/eve_new/following`
    2. Проверить статус ответа
    3. Проверить поля пагинации и массив `items`

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * `items` равен пустому массиву `[]`.
    * `total` равен `0`.
    * `pages` равен `0` или `1`, в зависимости от принятой продуктовой логики пагинации.
    * Ошибка `404` или `500` не возвращается.

### TC-FLWING-04. Пользователи в списке реально являются following
* **Описание:** Проверка, что каждый пользователь в ответе действительно является аккаунтом, на который подписан пользователь из path-параметра.
* **Обоснование:** Делаем эту проверку, потому что список following должен отражать реальные исходящие подписки; неверные пользователи в списке ломают социальную модель и счетчики профиля.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * У `alice_dev` есть исходящие подписки.
    * Доступна проверка через БД или ожидаемые тестовые данные.
* **Шаги:**
    1. Выполнить GET `/api/users/alice_dev/following`
    2. Сохранить список `username` из `items`
    3. Сверить этих пользователей с данными подписок в БД или с ожидаемыми тестовыми данными
    4. Выполнить GET `/api/users/alice_dev` и сравнить `following_count` с `total`

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Каждый пользователь из `items` действительно является аккаунтом, на который подписан `alice_dev`.
    * Поле `total` совпадает с количеством following по данным профиля/БД.

### TC-FLWING-05. Текущий пользователь видит свои following
* **Описание:** Проверка списка following для текущего авторизованного пользователя.
* **Обоснование:** Делаем эту проверку, потому что экран "мои подписки" должен показывать актуальный список аккаунтов, на которые подписан текущий пользователь; ошибка здесь напрямую ломает пользовательский сценарий управления подписками.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * `alice_dev` подписан хотя бы на одного пользователя.
* **Шаги:**
    1. Выполнить GET `/api/auth/me` и убедиться, что текущий пользователь `alice_dev`
    2. Выполнить GET `/api/users/alice_dev/following`
    3. Проверить список `items`

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Ответ содержит пользователей, на которых подписан `alice_dev`.
    * Список не содержит самого `alice_dev`, если self-follow запрещен бизнес-логикой.

### TC-FLWING-06. Following приватного пользователя
* **Описание:** Проверка поведения списка following для пользователя с приватным профилем.
* **Обоснование:** Делаем эту проверку, потому что приватность может влиять на доступ к социальным спискам; API должен иметь предсказуемое правило доступа к following приватного профиля.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
    * Пользователь `dave_quiet` имеет `is_private=true`.
    * `eve_new` не имеет подтвержденной подписки на `dave_quiet`.
* **Шаги:**
    1. Выполнить GET `/api/users/dave_quiet`
    2. Убедиться, что `is_private=true` и `is_following=false`
    3. Выполнить GET `/api/users/dave_quiet/following`

* **Ожидаемый результат:**
    * Статус: `200 OK` с допустимым списком following или `403 Forbidden`, в зависимости от продуктовой логики приватности.
    * **Критично:** поведение должно быть согласовано с правилами приватности продукта.
    * Ошибка `500 Internal Server Error` не возвращается.

### TC-FLWING-07. Заблокированные пользователи не попадают в following
* **Описание:** Проверка, что inactive/banned пользователи не отображаются в списке following обычного пользователя.
* **Обоснование:** Делаем эту проверку, потому что заблокированные аккаунты не должны участвовать в публичной социальной активности; их отображение может раскрывать нежелательные профили и искажать список подписок.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * В базе есть `frank_banned` со статусом `is_active=false`.
    * Если кто-то подписан на `frank_banned`, подготовить проверяемое состояние в БД.
* **Шаги:**
    1. Выполнить GET `/api/users/alice_dev/following`
    2. Проверить каждый объект в `items`
    3. Убедиться, что среди following нет `frank_banned`

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * В `items` отсутствует пользователь `frank_banned`.
    * Список содержит только активных пользователей, если продуктовая логика исключает inactive users.

### TC-FLWING-08. Проверка структуры `PaginatedResponse_UserBrief`
* **Описание:** Проверка соответствия ответа OpenAPI-схеме `PaginatedResponse_UserBrief`.
* **Обоснование:** Делаем эту проверку, потому что frontend зависит от стабильной структуры пагинации и краткого профиля пользователя; неверный контракт может сломать экран following.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * У `alice_dev` есть хотя бы одна исходящая подписка.
* **Шаги:**
    1. Выполнить GET `/api/users/alice_dev/following`
    2. Проверить верхнеуровневые поля ответа
    3. Проверить структуру каждого объекта в `items`

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Ответ содержит поля:
        - `items` (array)
        - `total` (integer)
        - `page` (integer)
        - `per_page` (integer)
        - `pages` (integer)
    * Каждый объект в `items` содержит поля `UserBrief`:
        - `id` (string, UUID)
        - `username` (string)
        - `display_name` (string)
        - `avatar_url` (string или null)
        - `is_verified` (boolean)
    * В объектах отсутствуют приватные поля полного профиля, например `email`, `role`, `is_active`.

### TC-FLWING-09. Запрос без токена (Unauthorized)
* **Описание:** Проверка запрета доступа к списку following без авторизации.
* **Обоснование:** Делаем эту проверку, потому что endpoint защищен `HTTPBearer`; без токена сервер не должен раскрывать социальные связи пользователей.
* **Предусловие:** Нет.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET Following**
    2. Проверить URL: `http://localhost:8000/api/users/alice_dev/following`
    3. Во вкладке **Auth** выбрать "No Auth"
    4. Убедиться, что заголовок `Authorization` отсутствует
    5. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized` или `403 Forbidden`
    * Ответ содержит сообщение об ошибке авторизации:
    ```json
    {
        "detail": "Not authenticated"
    }
    ```
    * Список following не возвращается как успешный ответ.

### TC-FLWING-10. Запрос с некорректным токеном
* **Описание:** Проверка обработки невалидного Bearer token.
* **Обоснование:** Делаем эту проверку, потому что сервер должен валидировать токен перед выдачей социальных связей; принятие случайной строки вместо токена создает риск несанкционированного доступа.
* **Предусловие:** Нет.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET Following**
    2. Во вкладке **Auth** выбрать тип "Bearer Token"
    3. Вставить невалидный токен:
       ```text
       invalid_token_12345
       ```
    4. Выполнить GET `/api/users/alice_dev/following`

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized` или `403 Forbidden`
    * Ответ содержит сообщение о невозможности проверить учетные данные:
    ```json
    {
        "detail": "Could not validate credentials"
    }
    ```
    * Список following не возвращается.

### TC-FLWING-11. Запрос с просроченным токеном
* **Описание:** Проверка запрета доступа с истекшим `access_token`.
* **Обоснование:** Делаем эту проверку, потому что access token имеет ограниченный срок жизни; если API принимает просроченные токены, старая сессия сможет читать социальные связи.
* **Предусловие:**
    * Есть `access_token`, срок действия которого истек, или тестовая среда позволяет подготовить expired token.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET Following**
    2. Во вкладке **Auth** вставить просроченный Bearer Token
    3. Выполнить GET `/api/users/alice_dev/following`

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized`
    * Ответ содержит сообщение об истекшем или невалидном токене:
    ```json
    {
        "detail": "Token has expired"
    }
    ```
    * Список following не возвращается.

### TC-FLWING-12. Несуществующий `username`
* **Описание:** Проверка ответа при запросе following пользователя, которого нет в базе.
* **Обоснование:** Делаем эту проверку, потому что клиент может открыть старую или некорректную ссылку; API должен отличать несуществующего пользователя от существующего пользователя без подписок.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * В базе отсутствует пользователь `unknown_user_999`.
* **Шаги:**
    1. Выполнить запрос:
       ```text
       GET http://localhost:8000/api/users/unknown_user_999/following
       ```
    2. Проверить статус и тело ответа

* **Ожидаемый результат:**
    * Статус: `404 Not Found`
    * Ответ содержит сообщение о том, что пользователь не найден:
    ```json
    {
        "detail": "User not found"
    }
    ```
    * Статус `200 OK` с пустым списком не возвращается для несуществующего пользователя, если продукт различает "нет пользователя" и "нет following".

### TC-FLWING-13. `username` с некорректными символами
* **Описание:** Проверка обработки значения `username`, которое содержит символы, не используемые в валидных username.
* **Обоснование:** Делаем эту проверку, потому что path-параметр может быть введен вручную; API должен безопасно обработать некорректное значение и не падать.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
* **Шаги:**
    1. Выполнить запрос с URL-encoded значением:
       ```text
       GET http://localhost:8000/api/users/%40%23%24%25/following
       ```
    2. Проверить статус и тело ответа

* **Ожидаемый результат:**
    * Статус: `404 Not Found` или `422 Unprocessable Entity`, в зависимости от реализации валидации path-параметра.
    * **Критично:** отсутствует ошибка `500 Internal Server Error`.
    * Список following существующего пользователя не возвращается.

### TC-FLWING-14. SQL-инъекция в `username`
* **Описание:** Проверка устойчивости endpoint'а к injection payload в path-параметре `username`.
* **Обоснование:** Делаем эту проверку, потому что `username` используется для поиска пользователя; небезопасная обработка может привести к SQL-инъекции или возврату чужих социальных связей.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
* **Шаги:**
    1. Выполнить запрос с URL-encoded payload:
       ```text
       GET http://localhost:8000/api/users/%27%20OR%201%3D1%20--/following
       ```
    2. Проверить статус и тело ответа

* **Ожидаемый результат:**
    * Статус: `404 Not Found` или `422 Unprocessable Entity`.
    * **Критично:** отсутствует ошибка `500 Internal Server Error`.
    * API не возвращает following первого пользователя из базы и не возвращает общий список пользователей.
    * SQL payload обрабатывается как обычное значение path-параметра.

### TC-FLWING-15. `page` меньше минимального значения
* **Описание:** Проверка нижней границы параметра `page`.
* **Обоснование:** Делаем эту проверку, потому что страницы начинаются с `1`; значение `0` может привести к некорректному offset и ошибкам пагинации.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
* **Шаги:**
    1. Выполнить запрос:
       ```text
       GET http://localhost:8000/api/users/alice_dev/following?page=0
       ```
    2. Проверить ответ

* **Ожидаемый результат:**
    * Статус: `422 Unprocessable Entity`
    * Ответ содержит ошибку валидации для query-параметра `page`.
    * В ошибке указано, что значение должно быть больше или равно `1`.

### TC-FLWING-18. Некорректный тип `page` и `per_page`
* **Описание:** Проверка обработки строковых значений в числовых query-параметрах.
* **Обоснование:** Делаем эту проверку, потому что `page` и `per_page` должны быть integer; если сервер не валидирует типы, пагинация может работать непредсказуемо или приводить к 500 ошибкам.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
* **Шаги:**
    1. Выполнить запрос:
       ```text
       GET http://localhost:8000/api/users/alice_dev/following?page=abc&per_page=test
       ```
    2. Проверить ответ

* **Ожидаемый результат:**
    * Статус: `422 Unprocessable Entity`
    * Ответ содержит ошибки валидации для query-параметров `page` и `per_page`.
    * **Критично:** отсутствует ошибка `500 Internal Server Error`.
