# Ручное тестирование API (Project: QA Sandbox)

В данном документе представлены тест-кейсы для ручного тестирования API эндпоинта `/api/auth/me`.
Объект тестирования: [QA Automation Sandbox](https://github.com/manikosto/qa-automation-sandbox)

Эндпоинт защищен. Перед выполнением тестов необходимо получить `access_token` через Login и подставить его в заголовок `Authorization: Bearer <token>`.

## Тест-кейсы (TC)

### TC-ME-01. Успешное получение данных текущего пользователя (Happy Path)
* **Обоснование:** Делаем эту проверку, потому что основная функция эндпоинта — предоставить пользователю актуальную информацию о его профиле. Это ключевой сценарий для работы приложения (например, отображение профиля в меню).
* **Предусловие:** 
    * Пользователь `alice@buzzhive.com` зарегистрирован и активен.
    * Получен актуальный `access_token` через `/api/auth/login`.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET Me**
    2. Проверить, что URL запроса: `http://localhost:8000/api/auth/me`
    3. Во вкладке **Auth** выбрать тип "Bearer Token" и вставить актуальный токен
    4. Нажать кнопку **Send**

* **Ожидаемый результат:** 
    * Статус: `200 OK`
    * Тело ответа содержит полную информацию о пользователе в формате JSON:
    ```json
    {
        "id": "uuid-строка",
        "email": "alice@buzzhive.com",
        "username": "alice_dev",
        "display_name": "Alice Developer",
        "bio": "строка или null",
        "avatar_url": "строка или null",
        "cover_url": "строка или null",
        "role": "user",
        "is_active": true,
        "is_verified": true,
        "is_private": false,
        "created_at": "ISO 8601 дата-время",
        "updated_at": "ISO 8601 дата-время",
        "followers_count": 0,
        "following_count": 0,
        "posts_count": 0,
        "is_following": false,
        "is_followed_by": false
    }
    ```

### TC-ME-02. Запрос без токена (Unauthorized)
* **Обоснование:** Делаем эту проверку, потому что эндпоинт содержит приватные данные пользователя (email, настройки профиля) и не должен быть доступен анонимным пользователям. Это базовая проверка безопасности.
* **Предусловие:** Нет.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET Me**
    2. Проверить, что URL запроса: `http://localhost:8000/api/auth/me`
    3. Во вкладке **Auth** выбрать "No Auth" (убедиться, что заголовок Authorization отсутствует)
    4. Нажать кнопку **Send**

* **Ожидаемый результат:** 
    * Статус: `403 Unauthorized`
    * Тело ответа:
    ```json
    {
        "detail": "Not authenticated"
    }
    ```

--- 

### TC-ME-03. Запрос с некорректным токеном
* **Обоснование:** Делаем эту проверку, потому что сервер должен валидировать подпись и формат токена. Принятие случайных строк вместо JWT создает уязвимость в системе безопасности.
* **Предусловие:** Нет.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET Me**
    2. Проверить, что URL запроса: `http://localhost:8000/api/auth/me`
    3. Во вкладке **Auth** выбрать тип "Bearer Token" и вставить невалидную строку (например, `invalid_token_12345`)
    4. Нажать кнопку **Send**

* **Ожидаемый результат:** 
    * Статус: `401 Unauthorized` 
    * Тело ответа:
    ```json
    {
    "detail": "Invalid or expired token",
    "error_code": "UNAUTHORIZED",
    "status_code": 401
    }   
    ```
    *Примечание: Точное сообщение может варьироваться, но статус должен быть 401 или 403.*

--- 

### TC-ME-04. Запрос с просроченным токеном
* **Обоснование:** Делаем эту проверку, потому что токены имеют ограниченный срок жизни (обычно 30 минут для access_token). Использование просроченного токена не должно давать доступ к защищенным ресурсам.
* **Предусловие:** 
    * Есть `access_token`, полученный более 30 минут назад (если время жизни токена по умолчанию — 30 минут).
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET Me**
    2. Проверить, что URL запроса: `http://localhost:8000/api/auth/me`
    3. Во вкладке **Auth** вставить просроченный токен
    4. Нажать кнопку **Send**

* **Ожидаемый результат:** 
    * Статус: `401 Unauthorized`
    * Тело ответа:
    ```json
    {
    "detail": "Invalid or expired token",
    "error_code": "UNAUTHORIZED",
    "status_code": 401
    }   
    ```

### TC-ME-05. Запрос с отозванным токеном (после Logout)
* **Обоснование:** Делаем эту проверку, потому что после выхода из системы токен должен быть внесен в черный список (token blacklist). Использование старого токена после logout — это дыра в безопасности, которая может привести к несанкционированному доступу.
* **Предусловие:** 
    * Пользователь успешно выполнил logout через `/api/auth/logout`.
    * Сохранен `access_token`, который был использован для logout.
* **Шаги:**
    1. Выполнить успешный Logout (POST `/api/auth/logout` с валидным токеном)
    2. В коллекции **QA Sandbox API** выбрать запрос **GET Me**
    3. Во вкладке **Auth** вставить тот же самый токен, который был отозван
    4. Нажать кнопку **Send**

* **Ожидаемый результат:** 
    * Статус: `401 Unauthorized`
    * Тело ответа:
    ```json
    {
    "detail": "Invalid or expired token",
    "error_code": "UNAUTHORIZED",
    "status_code": 401
    }
    ```
    *Примечание: Сообщение может отличаться, но доступ должен быть запрещен.*

### TC-ME-06. Корректность возвращаемых полей
* **Обоснование:** Делаем эту проверку, потому что клиентское приложение полагается на определенную структуру данных. Отсутствие обязательных полей или неверные типы данных могут привести к ошибкам в UI или логике приложения.
* **Предусловие:** 
    * Пользователь `alice@buzzhive.com` авторизован.
    * Получен актуальный `access_token`.
* **Шаги:**
    1. Выполнить успешный запрос GET `/api/auth/me` (как в TC-ME-01)
    2. Проверить наличие всех обязательных полей в ответе
    3. Проверить типы данных полей

* **Ожидаемый результат:** 
    * Статус: `200 OK`
    * Ответ содержит все обязательные поля согласно схеме `UserResponse`:
        - `id` (string, UUID формат)
        - `email` (string)
        - `username` (string)
        - `display_name` (string)
        - `bio` (string или null)
        - `avatar_url` (string или null)
        - `cover_url` (string или null)
        - `role` (string: "user", "moderator", "admin")
        - `is_active` (boolean)
        - `is_verified` (boolean)
        - `is_private` (boolean)
        - `created_at` (string, ISO 8601 date-time)
        - `updated_at` (string, ISO 8601 date-time)
        - `followers_count` (integer)
        - `following_count` (integer)
        - `posts_count` (integer)
        - `is_following` (boolean)
        - `is_followed_by` (boolean)

### TC-ME-07. Получение данных пользователя с различными ролями
* **Обоснование:** Делаем эту проверку, потому что роль пользователя определяет его права доступа в системе. Необходимо убедиться, что эндпоинт корректно возвращает информацию о роли (admin, moderator, user) для последующей проверки прав в клиентском приложении.
* **Предусловие:** В системе есть пользователи с разными ролями.
* **Шаги:**
    1. Авторизоваться как `admin@buzzhive.com` / `admin123`
    2. Выполнить запрос GET `/api/auth/me`
    3. Проверить, что `role` в ответе равен `"admin"`
    4. Повторить шаги 1-3 для `mod@buzzhive.com` (ожидаем `role: "moderator"`)
    5. Повторить шаги 1-3 для `alice@buzzhive.com` (ожидаем `role: "user"`)

* **Ожидаемый результат:** 
    * Для каждого пользователя:
        - Статус: `200 OK`
        - Поле `role` корректно отражает назначенную роль:
            - `admin@buzzhive.com` → `"role": "admin"`
            - `mod@buzzhive.com` → `"role": "moderator"`
            - `alice@buzzhive.com` → `"role": "user"`
