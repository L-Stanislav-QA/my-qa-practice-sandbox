# Ручное тестирование API (Project: QA Sandbox)

В данном документе представлены тест-кейсы для ручного тестирования API эндпоинта `POST /api/users/me/avatar`.
Объект тестирования: [QA Automation Sandbox](https://github.com/manikosto/qa-automation-sandbox)

# Примечание:
Все тесты выполняются в инструменте Postman. Запросы организованы в коллекцию "QA Sandbox API".
Для всех запросов используется базовый URL: `http://localhost:8000`

# Примечание по авторизации:
Эндпоинт защищен. Перед выполнением тестов необходимо получить `access_token` через Login и подставить его в заголовок `Authorization: Bearer <token>`.

# Примечание по формату запроса:
Эндпоинт принимает `multipart/form-data`. В Body необходимо выбрать тип `form-data`, добавить поле `file`, выбрать тип поля `File` и прикрепить файл изображения.

### TC-AVA-UP-01. Успешная загрузка avatar JPG (Happy Path)
* **Описание:** Проверка успешной загрузки изображения JPG в качестве аватара текущего пользователя.
* **Обоснование:** Делаем эту проверку, потому что загрузка аватара - основной сценарий ручки; пользователь должен иметь возможность персонализировать профиль изображением.
* **Предусловие:**
    * Сервер и база данных запущены.
    * Пользователь `eve@buzzhive.com` авторизован.
    * Получен актуальный `access_token`.
    * Подготовлен валидный JPG-файл, например `avatar.jpg`.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **POST Upload Avatar**
    2. Проверить, что URL запроса: `http://localhost:8000/api/users/me/avatar`
    3. Во вкладке **Auth** выбрать тип "Bearer Token" и вставить актуальный `access_token`
    4. Во вкладке **Body** выбрать `form-data`
    5. Добавить поле `file`, тип поля `File`
    6. Прикрепить файл `avatar.jpg`
    7. Нажать кнопку **Send**

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Ответ содержит `UserResponse`.
    * Поле `avatar_url` содержит строку со ссылкой/путем к загруженному аватару.
    * Поля `id`, `email`, `username`, `role` не изменились.

### TC-AVA-UP-03. Повторная загрузка аватара
* **Описание:** Проверка замены ранее загруженного аватара новым файлом.
* **Обоснование:** Делаем эту проверку, потому что пользователь может менять аватар несколько раз; API должен корректно обновлять ссылку и не оставлять профиль в старом состоянии.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
    * У пользователя уже есть загруженный аватар.
    * Подготовлен второй валидный файл `avatar_new.jpg`.
* **Шаги:**
    1. Выполнить GET `/api/auth/me` и сохранить текущее значение `avatar_url`
    2. Выполнить POST `/api/users/me/avatar` с новым файлом `avatar_new.jpg` в поле `file`
    3. Проверить ответ
    4. Выполнить повторный GET `/api/auth/me`

* **Ожидаемый результат:**
    * Статус POST: `200 OK`
    * Новый `avatar_url` заполнен.
    * После GET `/api/auth/me` возвращается новый `avatar_url`.
    * Если реализация генерирует уникальные URL для файлов, новый `avatar_url` отличается от старого.

### TC-AVA-UP-04. Проверка сохранения `avatar_url` через GET Me
* **Описание:** Проверка, что загруженный аватар сохраняется и возвращается при чтении текущего профиля.
* **Обоснование:** Делаем эту проверку, потому что успешный ответ upload не гарантирует сохранение данных; важно убедиться, что `avatar_url` записан в профиль и будет доступен UI после перезагрузки страницы.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
    * Подготовлен валидный файл изображения.
* **Шаги:**
    1. Выполнить POST `/api/users/me/avatar` с валидным файлом в поле `file`
    2. Сохранить `avatar_url` из ответа
    3. Выполнить GET `/api/auth/me`
    4. Сравнить `avatar_url` из ответа upload и GET Me

* **Ожидаемый результат:**
    * POST возвращает `200 OK`.
    * GET `/api/auth/me` возвращает `200 OK`.
    * `avatar_url` после GET Me совпадает со значением, полученным после upload, или указывает на тот же загруженный файл согласно правилам хранения.

* **Обоснование:** Делаем эту проверку, потому что загрузка аватара изменяет профиль конкретного пользователя; без токена сервер не должен принимать файл и менять данные аккаунта.

### TC-AVA-UP-08. Запрос с некорректным токеном
* **Описание:** Проверка обработки невалидного Bearer token.
* **Обоснование:** Делаем эту проверку, потому что сервер должен валидировать токен перед приемом файла; принятие случайной строки вместо токена создает риск несанкционированного изменения профиля.
* **Предусловие:**
    * Подготовлен валидный файл изображения.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **POST Upload Avatar**
    2. Во вкладке **Auth** выбрать тип "Bearer Token"
    3. Вставить невалидный токен:
       ```text
       invalid_token_12345
       ```
    4. Во вкладке **Body** выбрать `form-data` и прикрепить файл в поле `file`
    5. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized` или `403 Forbidden`
    * Ответ содержит сообщение о невозможности проверить учетные данные:
    ```json
    {
        "detail": "Could not validate credentials"
    }
    ```
    * Аватар пользователя не изменяется.

    4. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized`
    * Ответ содержит сообщение об истекшем или невалидном токене:

### TC-AVA-UP-12. JSON вместо multipart/form-data
* **Описание:** Проверка отправки JSON body вместо `multipart/form-data`.
* **Обоснование:** Делаем эту проверку, потому что endpoint ожидает binary-файл в multipart; неверный `Content-Type` должен быть отклонен предсказуемо, без серверной ошибки.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **POST Upload Avatar**
    2. Во вкладке **Auth** указать актуальный Bearer Token
    3. Во вкладке **Body** выбрать raw/JSON
    4. Отправить:
       ```json
       {
           "file": "avatar.jpg"
       }
       ```
    5. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `422 Unprocessable Entity` или `415 Unsupported Media Type`.
    * Ответ содержит ошибку о неверном формате тела запроса или отсутствующем файле.
    * **Критично:** отсутствует ошибка `500 Internal Server Error`.

    * Файл не сохраняется как аватар.
    * **Критично:** отсутствует ошибка `500 Internal Server Error`.

### TC-AVA-UP-15. Загрузка слишком большого файла
* **Описание:** Проверка поведения API при загрузке файла большого размера.
* **Обоснование:** Делаем эту проверку, потому что загрузка файлов может использоваться для перегрузки сервера; API должен иметь контролируемое поведение для oversized upload и не падать.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
    * Подготовлен файл изображения большого размера, например 10 MB или больше, если лимит продукта не известен.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **POST Upload Avatar**
    2. Во вкладке **Auth** указать актуальный Bearer Token
    3. Во вкладке **Body** выбрать `form-data`
    4. В поле `file` прикрепить большой файл изображения
    5. Нажать **Send**

* **Ожидаемый результат:**
    * Если размер в пределах лимита продукта: статус `200 OK`, `avatar_url` обновлен.
    * Если размер превышает лимит продукта: статус `413 Payload Too Large`, `400 Bad Request` или `422 Unprocessable Entity`.
    * **Критично:** отсутствует ошибка `500 Internal Server Error` и сервер продолжает отвечать на последующие запросы.

### TC-AVA-UP-16. Проверка метода GET вместо POST
* **Описание:** Проверка, что endpoint загрузки аватара не принимает неподдерживаемый HTTP-метод `GET`.
* **Обоснование:** Делаем эту проверку, потому что загрузка файла должна выполняться только через POST; принятие GET может означать некорректную настройку роутинга и нарушать HTTP-семантику.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
* **Шаги:**
    1. В Postman создать или выбрать запрос к URL `http://localhost:8000/api/users/me/avatar`
    2. Установить метод `GET`
    3. Во вкладке **Auth** указать актуальный Bearer Token
    4. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `405 Method Not Allowed` или `404 Not Found`, в зависимости от реализации роутинга.
    * Успешный статус `200 OK` не возвращается.
    * Аватар пользователя не изменяется.
