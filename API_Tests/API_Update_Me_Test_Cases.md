# Ручное тестирование API (Project: QA Sandbox)

В данном документе представлены тест-кейсы для ручного тестирования API эндпоинта `PATCH /api/users/me`.
Объект тестирования: [QA Automation Sandbox](https://github.com/manikosto/qa-automation-sandbox)

# Примечание:
Все тесты выполняются в инструменте Postman. Запросы организованы в коллекцию "QA Sandbox API".
Для всех запросов используется базовый URL: `http://localhost:8000`

# Примечание по авторизации:
Эндпоинт защищен. Перед выполнением тестов необходимо получить `access_token` через Login и подставить его в заголовок `Authorization: Bearer <token>`.

### TC-UPD-ME-01. Успешное обновление `display_name` (Happy Path)
* **Описание:** Проверка успешного изменения отображаемого имени текущего пользователя.
* **Обоснование:** Делаем эту проверку, потому что изменение `display_name` - базовая функция редактирования профиля; если она не работает, пользователь не сможет актуализировать публичное имя.
* **Предусловие:**
    * Сервер и база данных запущены.
    * Пользователь `eve@buzzhive.com` авторизован.
    * Получен актуальный `access_token`.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **PATCH Update Me**
    2. Проверить, что URL запроса: `http://localhost:8000/api/users/me`
    3. Во вкладке **Auth** выбрать тип "Bearer Token" и вставить актуальный `access_token`
    4. На вкладке **Body** выбрать raw/JSON и отправить:
       ```json
       {
           "display_name": "Eve Updated"
       }
       ```
    5. Нажать кнопку **Send**

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Ответ содержит `UserResponse`.
    * Поле `display_name` равно `"Eve Updated"`.
    * Поля `id`, `email`, `username`, `role` остались прежними.

### TC-UPD-ME-07. Проверка неизменяемых полей
* **Описание:** Проверка, что endpoint не позволяет изменить поля вне схемы `UserUpdate`.
* **Обоснование:** Делаем эту проверку, потому что через редактирование профиля нельзя повышать роль, менять email или username; если сервер принимает такие поля, это риск нарушения прав доступа и целостности аккаунта.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
    * Перед тестом сохранены текущие значения `email`, `username`, `role`.
* **Шаги:**
    1. Выполнить PATCH `/api/users/me` с body:
       ```json
       {
           "email": "hacked@example.com",
           "username": "hacked_user",
           "role": "admin",
           "display_name": "Safe Display Name"
       }
       ```
    2. Проверить ответ PATCH
    3. Выполнить GET `/api/auth/me`
    4. Проверить значения `email`, `username`, `role`

* **Ожидаемый результат:**
    * Статус PATCH: `200 OK` или `422 Unprocessable Entity`, в зависимости от политики обработки лишних полей.
    * Если запрос принят, изменяется только разрешенное поле `display_name`.
    * Поля `email`, `username`, `role` остаются прежними.
    * Пользователь не получает роль `admin`.

    * Ответ содержит ошибку о том, что тело запроса обязательно.

* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **PATCH Update Me**
    2. Во вкладке **Auth** указать актуальный Bearer Token
    3. На вкладке **Body** выбрать raw/JSON и отправить некорректный JSON:
       ```json
       {
           "display_name": "Broken JSON",
       }
       ```
    4. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `422 Unprocessable Entity` или `400 Bad Request`.
    * Ответ содержит сообщение об ошибке парсинга JSON.
    * **Критично:** отсутствует ошибка `500 Internal Server Error`.
