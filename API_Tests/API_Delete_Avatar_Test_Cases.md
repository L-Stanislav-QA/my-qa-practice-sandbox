# Ручное тестирование API (Project: QA Sandbox)

В данном документе представлены тест-кейсы для ручного тестирования API эндпоинта `DELETE /api/users/me/avatar`.
Объект тестирования: [QA Automation Sandbox](https://github.com/manikosto/qa-automation-sandbox)

# Примечание:
Все тесты выполняются в инструменте Postman. Запросы организованы в коллекцию "QA Sandbox API".
Для всех запросов используется базовый URL: `http://localhost:8000`

# Примечание по авторизации:
Эндпоинт защищен. Перед выполнением тестов необходимо получить `access_token` через Login и подставить его в заголовок `Authorization: Bearer <token>`.

# Примечание по формату ответа:
При успешном удалении аватара endpoint возвращает `204 No Content`. Тело ответа должно быть пустым.

### TC-AVA-DEL-01. Успешное удаление аватара (Happy Path)
* **Описание:** Проверка успешного удаления аватара текущего пользователя.
* **Обоснование:** Делаем эту проверку, потому что пользователь должен иметь возможность удалить изображение профиля; если удаление не работает, пользователь не сможет убрать устаревший или нежелательный аватар.
* **Предусловие:**
    * Сервер и база данных запущены.
    * Пользователь `eve@buzzhive.com` авторизован.
    * Получен актуальный `access_token`.
    * У пользователя `eve_new` уже загружен аватар через POST `/api/users/me/avatar`.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **DELETE Avatar**
    2. Проверить, что URL запроса: `http://localhost:8000/api/users/me/avatar`
    3. Во вкладке **Auth** выбрать тип "Bearer Token" и вставить актуальный `access_token`
    4. Тело запроса не отправлять
    5. Нажать кнопку **Send**

* **Ожидаемый результат:**
    * Статус: `204 No Content`
    * Тело ответа пустое.
    * Ошибка не возвращается.

### TC-AVA-DEL-02. Проверка очистки `avatar_url` через GET Me
* **Описание:** Проверка, что после удаления аватара поле `avatar_url` очищается в профиле текущего пользователя.
* **Обоснование:** Делаем эту проверку, потому что статус `204` сам по себе не гарантирует изменение данных; важно убедиться, что профиль больше не ссылается на удаленный аватар.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
    * У пользователя есть загруженный аватар.
* **Шаги:**
    1. Выполнить GET `/api/auth/me` и убедиться, что `avatar_url` не равен `null`
    2. Выполнить DELETE `/api/users/me/avatar`
    3. Убедиться, что DELETE вернул `204 No Content`
    4. Выполнить GET `/api/auth/me`
    5. Проверить поле `avatar_url`

* **Ожидаемый результат:**
    * DELETE возвращает `204 No Content`.
    * GET `/api/auth/me` после удаления возвращает `200 OK`.
    * Поле `avatar_url` равно `null` или пустому значению, принятому в продукте для отсутствующего аватара.

### TC-AVA-DEL-03. Удаление аватара после повторной загрузки
* **Описание:** Проверка удаления аватара после того, как пользователь уже заменил старый аватар новым.
* **Обоснование:** Делаем эту проверку, потому что пользователь может несколько раз менять аватар, а затем удалить его; API должен работать корректно с актуальным состоянием, а не только с первым загруженным файлом.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
    * Подготовлены два валидных изображения `avatar_1.jpg` и `avatar_2.jpg`.
* **Шаги:**
    1. Выполнить POST `/api/users/me/avatar` с файлом `avatar_1.jpg`
    2. Выполнить POST `/api/users/me/avatar` с файлом `avatar_2.jpg`
    3. Выполнить GET `/api/auth/me` и убедиться, что `avatar_url` заполнен
    4. Выполнить DELETE `/api/users/me/avatar`
    5. Выполнить GET `/api/auth/me`

* **Ожидаемый результат:**
    * Оба POST-запроса возвращают `200 OK`.
    * DELETE возвращает `204 No Content`.
    * После удаления `avatar_url` очищен.
    * Профиль не возвращает ссылку на старый или новый аватар.

### TC-AVA-DEL-04. Повторное удаление аватара
* **Описание:** Проверка поведения API при повторном удалении, когда аватар уже отсутствует.
* **Обоснование:** Делаем эту проверку, потому что повторный DELETE может произойти из-за двойного клика, повторной отправки запроса или retry-логики; API должен отвечать предсказуемо и не падать.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
    * У пользователя отсутствует аватар (`avatar_url=null`).
* **Шаги:**
    1. Выполнить GET `/api/auth/me` и убедиться, что `avatar_url=null`
    2. Выполнить DELETE `/api/users/me/avatar`
    3. Сохранить статус ответа
    4. Выполнить DELETE `/api/users/me/avatar` повторно
    5. Проверить статус второго ответа

* **Ожидаемый результат:**
    * Первый DELETE возвращает `204 No Content` или `404 Not Found`, в зависимости от выбранной продуктовой логики.
    * Второй DELETE возвращает `204 No Content` или `404 Not Found`, но без `500 Internal Server Error`.
    * `avatar_url` остается пустым.

    3. Выполнить GET `/api/auth/me`

* **Ожидаемый результат:**
    * DELETE возвращает `204 No Content`.
    * Поле `avatar_url` очищено.
    * Поле `is_private` остается `true`.

### TC-AVA-DEL-06. Проверка, что удаляются только данные текущего пользователя
* **Описание:** Проверка, что удаление аватара влияет только на профиль пользователя, чей токен используется.
* **Обоснование:** Делаем эту проверку, потому что endpoint работает с `/me`; ошибка в определении текущего пользователя может привести к удалению чужого аватара и нарушению изоляции данных.
* **Предусловие:**
    * Пользователи `alice@buzzhive.com` и `bob@buzzhive.com` авторизованы в отдельных сессиях.
    * У обоих пользователей загружены аватары.
    * Сохранены `avatar_url` обоих пользователей.
* **Шаги:**
    1. С токеном `alice_dev` выполнить DELETE `/api/users/me/avatar`
    2. Выполнить GET `/api/auth/me` с токеном `alice_dev`
    3. Выполнить GET `/api/users/bob_photo` с токеном `alice_dev` или GET `/api/auth/me` с токеном `bob_photo`
    4. Проверить `avatar_url` у обоих пользователей

* **Ожидаемый результат:**
    * У `alice_dev` поле `avatar_url` очищено.
    * У `bob_photo` поле `avatar_url` осталось без изменений.
    * DELETE не влияет на чужие профили.

### TC-AVA-DEL-07. Проверка пустого тела ответа при 204
* **Описание:** Проверка, что успешный DELETE не возвращает тело ответа.
* **Обоснование:** Делаем эту проверку, потому что статус `204 No Content` по HTTP-семантике не должен содержать body; тело при 204 может ломать клиенты и автотесты, которые строго проверяют протокол.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
    * У пользователя есть загруженный аватар.
* **Шаги:**
    1. Выполнить DELETE `/api/users/me/avatar`
    2. Проверить статус ответа
    3. Проверить тело ответа в Postman

* **Ожидаемый результат:**
    * Статус: `204 No Content`.
    * Тело ответа пустое.
    * Заголовок `Content-Length`, если присутствует, равен `0`.

### TC-AVA-DEL-08. Запрос без токена (Unauthorized)
* **Описание:** Проверка запрета удаления аватара без авторизации.
* **Обоснование:** Делаем эту проверку, потому что удаление аватара изменяет профиль конкретного пользователя; без токена сервер не должен знать, чей аватар удалять, и не должен выполнять операцию.
* **Предусловие:** Нет.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **DELETE Avatar**
    2. Проверить URL: `http://localhost:8000/api/users/me/avatar`
    3. Во вкладке **Auth** выбрать "No Auth"
    4. Убедиться, что заголовок `Authorization` отсутствует
    5. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized` или `403 Forbidden`
    * Ответ содержит сообщение об ошибке авторизации:
    ```json
    {
        "detail": "Not authenticated"
    }
    ```
    * Никакой аватар не удаляется.

### TC-AVA-DEL-09. Запрос с некорректным токеном
* **Описание:** Проверка обработки невалидного Bearer token.
* **Обоснование:** Делаем эту проверку, потому что сервер должен валидировать токен перед изменением профиля; принятие случайной строки вместо токена создает риск несанкционированного удаления данных.
* **Предусловие:** Нет.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **DELETE Avatar**
    2. Во вкладке **Auth** выбрать тип "Bearer Token"
    3. Вставить невалидный токен:
       ```text
       invalid_token_12345
       ```
    4. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized` или `403 Forbidden`
    * Ответ содержит сообщение о невозможности проверить учетные данные:
    ```json
    {
        "detail": "Could not validate credentials"
    }
    ```
    * Никакой аватар не удаляется.

### TC-AVA-DEL-10. Запрос с просроченным токеном
* **Описание:** Проверка запрета удаления аватара с истекшим `access_token`.
* **Обоснование:** Делаем эту проверку, потому что access token имеет ограниченный срок жизни; если API принимает просроченные токены, старая сессия сможет изменять профиль.
* **Предусловие:**
    * Есть `access_token`, срок действия которого истек, или тестовая среда позволяет подготовить expired token.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **DELETE Avatar**
    2. Во вкладке **Auth** вставить просроченный Bearer Token
    3. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized`
    * Ответ содержит сообщение об истекшем или невалидном токене:
    ```json
    {
        "detail": "Token has expired"
    }
    ```
    * Аватар пользователя не изменяется.

### TC-AVA-DEL-11. DELETE с body в запросе
* **Описание:** Проверка поведения endpoint'а при отправке лишнего body в DELETE-запросе.
* **Обоснование:** Делаем эту проверку, потому что endpoint не описывает request body; клиент может случайно отправить тело, и API должен обработать это предсказуемо без серверной ошибки.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
    * У пользователя есть загруженный аватар.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **DELETE Avatar**
    2. Во вкладке **Auth** указать актуальный Bearer Token
    3. Во вкладке **Body** выбрать raw/JSON и отправить:
       ```json
       {
           "reason": "remove avatar"
       }
       ```
    4. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `204 No Content` или `422 Unprocessable Entity`, в зависимости от политики обработки лишнего body.
    * **Критично:** отсутствует ошибка `500 Internal Server Error`.
    * Если запрос принят, удаляется только аватар текущего пользователя.

### TC-AVA-DEL-12. DELETE с query-параметрами
* **Описание:** Проверка поведения endpoint'а при отправке лишних query-параметров.
* **Обоснование:** Делаем эту проверку, потому что endpoint не описывает query-параметры; лишние параметры не должны приводить к удалению чужих данных или серверной ошибке.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
    * У пользователя есть загруженный аватар.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **DELETE Avatar**
    2. Во вкладке **Auth** указать актуальный Bearer Token
    3. Выполнить запрос:
       ```text
       DELETE http://localhost:8000/api/users/me/avatar?user_id=some-other-user&force=true
       ```
    4. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `204 No Content` или `422 Unprocessable Entity`, в зависимости от политики обработки лишних query-параметров.
    * **Критично:** отсутствует ошибка `500 Internal Server Error`.
    * Если запрос принят, удаляется только аватар текущего пользователя, а query-параметр `user_id` не влияет на выбор пользователя.

### TC-AVA-DEL-13. Проверка метода POST вместо DELETE
* **Описание:** Проверка, что endpoint удаления аватара не принимает HTTP-метод `POST`.
* **Обоснование:** Делаем эту проверку, потому что для этого URL метод POST уже используется для загрузки аватара; важно не спутать удаление с загрузкой и не получить успешное удаление по неверному методу.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
* **Шаги:**
    1. В Postman создать или выбрать запрос к URL `http://localhost:8000/api/users/me/avatar`
    2. Установить метод `POST`
    3. Во вкладке **Auth** указать актуальный Bearer Token
    4. Не прикреплять файл
    5. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `422 Unprocessable Entity`, потому что POST ожидает multipart-поле `file`, или другая контролируемая ошибка.
    * Успешное удаление аватара не происходит.
    * **Критично:** POST без файла не должен удалять существующий аватар.

### TC-AVA-DEL-14. Проверка метода PATCH вместо DELETE
* **Описание:** Проверка, что endpoint удаления аватара не принимает HTTP-метод `PATCH`.
* **Обоснование:** Делаем эту проверку, потому что ручка удаления должна работать только через DELETE; поддержка PATCH для этого URL может указывать на ошибку роутинга.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
* **Шаги:**
    1. В Postman создать или выбрать запрос к URL `http://localhost:8000/api/users/me/avatar`
    2. Установить метод `PATCH`
    3. Во вкладке **Auth** указать актуальный Bearer Token
    4. Нажать **Send**

* **Ожидаемый результат:**
