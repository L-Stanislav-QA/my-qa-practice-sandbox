# Ручное тестирование API (Project: QA Sandbox)

В данном документе представлены тест-кейсы для ручного тестирования API эндпоинта `GET /api/users/suggestions`.
Объект тестирования: [QA Automation Sandbox](https://github.com/manikosto/qa-automation-sandbox)

# Примечание:
Все тесты выполняются в инструменте Postman. Запросы организованы в коллекцию "QA Sandbox API".
Для всех запросов используется базовый URL: `http://localhost:8000`

# Примечание по авторизации:
Эндпоинт защищен. Перед выполнением тестов необходимо получить `access_token` через Login и подставить его в заголовок `Authorization: Bearer <token>`.

### TC-SUG-01. Успешное получение рекомендаций (Happy Path)
* **Описание:** Проверка базового получения списка пользователей, рекомендованных текущему пользователю.
* **Обоснование:** Делаем эту проверку, потому что это основной сценарий ручки: авторизованный пользователь должен получать список людей, на которых он еще не подписан, чтобы расширять социальные связи внутри приложения.
* **Предусловие:**
    * Сервер и база данных запущены.
    * Пользователь `eve@buzzhive.com` авторизован.
    * Получен актуальный `access_token`.
    * В базе есть активные пользователи, на которых `eve_new` еще не подписан.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET Suggestions**
    2. Проверить, что URL запроса: `http://localhost:8000/api/users/suggestions`
    3. Во вкладке **Auth** выбрать тип "Bearer Token" и вставить актуальный `access_token`
    4. Нажать кнопку **Send**

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Ответ содержит массив пользователей:
    ```json
    [
        {
            "id": "uuid-строка",
            "username": "alice_dev",
            "display_name": "Alice Developer",
            "avatar_url": "строка или null",
            "is_verified": true
        }
    ]
    ```
    * Каждый элемент массива соответствует схеме `UserBrief`.
    * В массиве есть только пользователи, на которых текущий пользователь еще не подписан.

### TC-SUG-02. Проверка лимита до 5 пользователей
* **Описание:** Проверка, что ручка возвращает не больше 5 рекомендованных пользователей.
* **Обоснование:** Делаем эту проверку, потому что в описании API указано ограничение "Return up to 5 active users"; превышение лимита может перегружать UI-блок рекомендаций и нарушать контракт между backend и frontend.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
    * В базе есть больше 5 активных пользователей, на которых текущий пользователь не подписан, или тестовая база подготовлена под этот сценарий.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET Suggestions**
    2. Во вкладке **Auth** указать актуальный Bearer Token
    3. Выполнить запрос GET `/api/users/suggestions`
    4. Посчитать количество объектов в массиве ответа

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Количество элементов в массиве ответа меньше или равно `5`.
    * Если подходящих пользователей больше 5, API все равно возвращает максимум 5 объектов.

### TC-SUG-03. Рекомендации не содержат текущего пользователя
* **Описание:** Проверка, что текущий авторизованный пользователь не попадает в собственные рекомендации.
* **Обоснование:** Делаем эту проверку, потому что пользователь не может подписаться сам на себя; попадание текущего пользователя в рекомендации является ошибкой бизнес-логики и ухудшает качество рекомендаций.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
    * Известен `id` или `username` текущего пользователя: `eve_new`.
* **Шаги:**
    1. Выполнить GET `/api/auth/me` и сохранить `id` и `username` текущего пользователя
    2. Выполнить GET `/api/users/suggestions` с тем же `access_token`
    3. Проверить каждый объект в массиве ответа

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * В массиве ответа нет объекта с `username: "eve_new"`.
    * В массиве ответа нет объекта с `id`, равным `id` текущего пользователя.

### TC-SUG-04. Рекомендации не содержат уже following пользователей
* **Описание:** Проверка, что пользователи, на которых текущий пользователь уже подписан, не возвращаются в рекомендациях.
* **Обоснование:** Делаем эту проверку, потому что ручка должна предлагать новых пользователей для подписки; если уже подписанные пользователи снова появляются в рекомендациях, это ломает бизнес-смысл блока suggestions.
* **Предусловие:**
    * Пользователь `alice@buzzhive.com` авторизован.
    * У `alice_dev` есть хотя бы одна активная подписка.
    * Список following можно проверить через GET `/api/users/alice_dev/following` или в БД.
* **Шаги:**
    1. Выполнить GET `/api/users/alice_dev/following` и сохранить список `username` пользователей из `items`
    2. Выполнить GET `/api/users/suggestions` с токеном пользователя `alice_dev`
    3. Сравнить пользователей из ответа suggestions со списком following

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Ни один пользователь из списка following не присутствует в массиве ответа `/api/users/suggestions`.
    * Рекомендации содержат только пользователей, на которых `alice_dev` еще не подписан.

### TC-SUG-05. Рекомендации содержат только активных пользователей
* **Описание:** Проверка, что заблокированные или деактивированные пользователи не попадают в рекомендации.
* **Обоснование:** Делаем эту проверку, потому что API должен продвигать только доступные профили; рекомендация заблокированного пользователя создает плохой UX и может раскрыть профиль, который не должен участвовать в социальной активности.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
    * В базе есть пользователь `frank_banned` со статусом `is_active=false`.
    * При необходимости проверить в БД:
      ```sql
      SELECT username, is_active FROM users WHERE username='frank_banned';
      ```
* **Шаги:**
    1. Выполнить GET `/api/users/suggestions`
    2. Проверить список пользователей в массиве ответа
    3. Убедиться, что среди них нет `frank_banned`

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * В массиве ответа отсутствует пользователь `frank_banned`.
    * Все возвращенные пользователи являются активными.

### TC-SUG-06. Пустой список, когда некого рекомендовать
* **Описание:** Проверка корректного ответа, когда у текущего пользователя нет доступных рекомендаций.
* **Обоснование:** Делаем эту проверку, потому что empty state является нормальным бизнес-сценарием; API должен вернуть пустой массив, а не ошибку, чтобы UI мог корректно показать отсутствие рекомендаций.
* **Предусловие:**
    * Создан или выбран тестовый пользователь, который уже подписан на всех активных пользователей.
    * Пользователь авторизован, получен актуальный `access_token`.
* **Шаги:**
    1. Убедиться через БД или GET `/api/users/{username}/following`, что пользователь подписан на всех активных пользователей, кроме самого себя
    2. Выполнить GET `/api/users/suggestions`
    3. Проверить тело ответа

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Тело ответа:
    ```json
    []
    ```
    * Ошибка `404`, `422` или `500` не возвращается.

### TC-SUG-07. Запрос без токена (Unauthorized)
* **Описание:** Проверка запрета доступа к рекомендациям без авторизации.
* **Обоснование:** Делаем эту проверку, потому что рекомендации зависят от текущего пользователя; без токена сервер не знает, для кого строить список, и не должен раскрывать пользовательские данные анонимному клиенту.
* **Предусловие:** Нет.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET Suggestions**
    2. Проверить URL: `http://localhost:8000/api/users/suggestions`
    3. Во вкладке **Auth** выбрать "No Auth"
    4. Убедиться, что заголовок `Authorization` отсутствует
    5. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized` или `403 Forbidden`
    * Ответ содержит сообщение об ошибке авторизации:
    ```json
    {
        "detail": "Not authenticated"
    }
    ```
    * Массив рекомендаций не возвращается как успешный ответ.

### TC-SUG-08. Запрос с некорректным токеном
* **Описание:** Проверка обработки невалидного Bearer token.
* **Обоснование:** Делаем эту проверку, потому что сервер должен валидировать подпись и формат токена; принятие случайной строки вместо токена создает риск несанкционированного доступа к данным пользователей.
* **Предусловие:** Нет.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET Suggestions**
    2. Во вкладке **Auth** выбрать тип "Bearer Token"
    3. Вставить невалидный токен:
       ```text
       invalid_token_12345
       ```
    4. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized` или `403 Forbidden`
    * Ответ содержит сообщение о невозможности проверить учетные данные:
    ```json
    {
        "detail": "Could not validate credentials"
    }
    ```
    * Рекомендации не возвращаются.

### TC-SUG-09. Запрос с просроченным токеном
* **Описание:** Проверка запрета доступа с истекшим `access_token`.
* **Обоснование:** Делаем эту проверку, потому что access token имеет ограниченный срок жизни; если API принимает просроченные токены, пользовательская сессия становится небезопасной.
* **Предусловие:**
    * Есть `access_token`, срок действия которого истек, или тестовая среда позволяет подготовить expired token.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET Suggestions**
    2. Во вкладке **Auth** вставить просроченный Bearer Token
    3. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `401 Unauthorized`
    * Ответ содержит сообщение об истекшем или невалидном токене:
    ```json
    {
        "detail": "Token has expired"
    }
    ```
    * Рекомендации не возвращаются.

### TC-SUG-10. Проверка структуры `UserBrief`
* **Описание:** Проверка соответствия каждого объекта рекомендации схеме `UserBrief`.
* **Обоснование:** Делаем эту проверку, потому что frontend ожидает конкретный контракт данных; если API вернет лишние, отсутствующие или неверно типизированные поля, UI может работать нестабильно или раскрыть приватную информацию.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
    * В ответе `/api/users/suggestions` есть хотя бы один пользователь.
* **Шаги:**
    1. Выполнить GET `/api/users/suggestions`
    2. Проверить, что тело ответа является массивом
    3. Проверить структуру каждого объекта массива

* **Ожидаемый результат:**
    * Статус: `200 OK`
    * Каждый объект содержит поля:
        - `id` (string, UUID)
        - `username` (string)
        - `display_name` (string)
        - `avatar_url` (string или null)
        - `is_verified` (boolean)
    * В объектах отсутствуют приватные поля полного профиля, например:
        - `email`
        - `role`
        - `is_active`
        - `created_at`
        - `updated_at`

### TC-SUG-11. Лишние query-параметры в запросе
* **Описание:** Проверка поведения ручки при передаче query-параметров, не описанных в API-спецификации.
* **Обоснование:** Делаем эту проверку, потому что клиент или пользователь может случайно передать лишние параметры; API должен обработать такой запрос предсказуемо и не падать с 500 ошибкой.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
* **Шаги:**
    1. В коллекции **QA Sandbox API** выбрать запрос **GET Suggestions**
    2. Во вкладке **Auth** указать актуальный Bearer Token
    3. Во вкладке **Params** добавить:
       ```text
       page=1
       per_page=100
       sort_by=email
       ```
    4. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `200 OK` или `422 Unprocessable Entity` в зависимости от реализации обработки лишних query-параметров.
    * **Критично:** отсутствует ошибка `500 Internal Server Error`.
    * Если API игнорирует лишние параметры, ответ остается массивом `UserBrief` и содержит не больше 5 пользователей.

### TC-SUG-12. Проверка метода POST вместо GET
* **Описание:** Проверка, что эндпоинт не принимает неподдерживаемый HTTP-метод `POST`.
* **Обоснование:** Делаем эту проверку, потому что ручка предназначена только для чтения данных через GET; принятие POST может означать некорректную настройку роутинга и привести к непредсказуемому поведению API.
* **Предусловие:**
    * Пользователь `eve@buzzhive.com` авторизован.
* **Шаги:**
    1. В Postman создать или выбрать запрос к URL `http://localhost:8000/api/users/suggestions`
    2. Установить метод `POST`
    3. Во вкладке **Auth** указать актуальный Bearer Token
    4. Тело запроса не отправлять
    5. Нажать **Send**

* **Ожидаемый результат:**
    * Статус: `405 Method Not Allowed` или `404 Not Found`, в зависимости от реализации роутинга.
    * Успешный статус `200 OK` не возвращается.
    * Рекомендации не возвращаются как результат POST-запроса.
